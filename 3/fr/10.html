====[ motivation ]==============================================================

Les approches pour l'exécution ELF en mémoire[1] utilisent typiquement memfd_create() et
fexecve() qui dépendent de l'existence de descripteurs de fichiers dans le système de fichiers /proc
Ceci peut être contrôlé et détecté sans trop d'effort[2].
Par conséquent, les questions suivantes se posent :

 Est-il possible d'atteindre une exécution ELF en mémoire sans utiliser de
 descripteurs ?

 Si oui, peut-on le faire avec l'ensemble des outils par défaut d'une distribution Linux
 (c'est-à-dire sans installer d'outils supplémentaires) ?

La réponse est oui, grâce aux modules standards de Perl et un peu de peek & poke.

Cet article décrira l'implémentation de exec_elf64.pl, un script pour
l'exécution ELF en mémoire sans toucher le système de fichiers. This approach has
the following considerations:

 - Le contenu binaire ELF est codé en dur dans le code source du script.

 - L'ELF est analysé et chargé en mémoire.

 - Le processus de chargement prend en charge les réadressements et l'utilisation de symboles externes du
   objets partagés. Dans ce cas, les symboles externes sont chargés depuis glibc.

 - Prend en charge les ELF x64.

 - Le script est écrit en Perl, un langage interprété disponible par défaut
 sur la plupart des distributions Linux x64. La version 5.008001 ou supérieure est requise.

Le code source complet peut être trouvé à :

    https://git.sr.ht/~hckng/elf/tree/master/item/exec_elf64.pl
    https://github.com/ilv/elf/blob/main/exec_elf64.pl


====[ préliminaires  ]=====================================================

Les étapes pour charger et exécuter un ELF en mémoire peuvent être résumées ainsi
follows:

 1) Lire le contenu binaire ELF.
 2) Analyser les en-têtes ELF (sections, segments, etc).
 3) Utiliser les informations d'en-tête pour mapper le code et les données ELF en mémoire.
 4) Appliquer les réadressements (y compris les symboles externes).
 5) Exécuter les fonctions ELF mappées.

Chacune de ces étapes sera discutée dans les sections suivantes, considering the
following ELF object:

------------------------------ START obj.c -------------------------------------
 #include 

 void print_japh(void) {
     putchar('j');
     putchar('a');
     putchar('p');
     putchar('h');
     putchar('\n');
 }

 int main(void) {
     char *str = "i am an elf";

     printf("%s\n", str);
     print_japh();

     return 0;
 }
------------------------------- END obj.c --------------------------------------

 $ gcc -c obj.c
 $ file obj.o
 obj.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped


====[ partie 1 : lire ELF ]========================================================

L'approche usuelle pour ouvrir un fichier et effectuer des opérations d'entrée/sortie (such as
read, write, seek, etc.) is by specifying a path to an existing file on the
existant sur le système de fichiers ou en spécifiant un descripteur de fichier, which in some cases may represent
an "anonymous" or mémoire-only file[1]. These options require interaction with
the regular filesystem and proc filesystem respectivement.

Cependant, Perl fournit une méthode alternative pour ouvrir un filehandle en utilisant une
référence à une variable scalaire au lieu d'un nom de fichier. Consider the following:

--------------------------------------------------------------------------------
my $buff;
my $str = "hello world";

open my $fh, '<', \$str;
read $fh, $buff, 5;
close $fh;

print "content read: $buff\n";
--------------------------------------------------------------------------------

Le code ci-dessus crée un filehandle $fh en utilisant une référence à la chaîne $str and
successfully reads 5 bytes into $buff by using the read() function. This method
can also be applied to open the contents of an ELF object from a string
de référence et effectuer des opérations d'entrée/sortie sur lui.

Premièrement, la sous-routine read_elf() est définie comme suit :

--------------------------------------------------------------------------------
 sub read_elf {
     my $code = get_code();
     open my $fh, '<:raw', \$code;

     return ($code, $fh);
 }
--------------------------------------------------------------------------------

La chaîne $code et le filehandle $fh sont retournés car les deux seront utilisés
plus tard pendant les processus d'analyse et de cartographie. Pour créer la chaîne $code,
l'utilisation suivante de perl est utilisée :

 $ perl -e 'print"my \$code = \"\";\n";$/=\32;' \
 -e 'print"\$code .= pack q/H*/, q/".(unpack"H*")."/;\n" while(<>)' ./obj.o

La commande ci-dessus génère une chaîne $code qui contient les données binaires de l'objet ELF.
La chaîne $code peut ensuite être incluse dans la sous-routine get_code() :

--------------------------------------------------------------------------------
 sub get_code {
     my $code = "";
     $code .= pack q/H*/, q/7f454c460201010000000000[...]000000000000000000000/;
     $code .= pack q/H*/, q/000000000000000018040000[...]40000000040000d000c00/;
     $code .= pack q/H*/, q/554889e5bf6a000000e80000[...]f6000bf70000000e80000/;
     $code .= pack q/H*/, q/0000bf68000000e800000000[...]00000e3554889e54883ec/;
     [...]
     [...]
     $code .= pack q/H*/, q/000000000000000000000000[...]000006100000000000000/;
     $code .= pack q/H*/, q/000000000000000001000000[...]000000000000000000/;
     return $code;
 }
--------------------------------------------------------------------------------

Pour plus de simplicité, la sous-routine get_code() est définie à la fin du
script exec_elf64.pl pour faciliter le remplacement de la chaîne $code par une nouvelle.


====[ partie 2 : analyser ELF ]=======================================================

Perl ne fournit pas de module standard pour l'analyse des ELF. However, the unpack()
function can be used to extract the ELF's binary content based on a set of fixed
data templates[3]:

 - "C", une valeur unsigned char (1 octet).
 - "a", une chaîne avec des données binaires arbitraires (1 octet).
 - "x", un octet nul.
 - "S", une valeur unsigned short (2 octets).
 - "i", un entier signé (4 octets).
 - "I", un entier non signé (4 octets).
 - "q", une valeur quad signée (8 octets).
 - "Q", Une valeur quad non signée (8 octets).

L'en-tête ELF, la table des en-têtes de section, la table des symboles, la table des
chaînes et les relocalisations sont analysés principalement basés sur les
spécifications référencées Linux[4][5][6][7] et la logique implémentée dans readelf.pl[8].

For the purpose of this work, deux sous-routines auxiliaires ru() and mk_hash() are
defined pour la lecture/déballage de données et pour la création de hachages associated to the
parsed headers, respectivement. Then, the initial ELF header is read and parsed
as follows (using the field names defined in @e_keys):

--------------------------------------------------------------------------------
# elf header keys
my @e_keys = (
    'ei_mag0', 'ei_mag1', 'ei_mag2', 'ei_mag3', 'ei_class', 'ei_data',
    'ei_version', 'ei_osabi', 'ei_abiversion', #ei_pad ignored
    'e_type', 'e_machine', 'e_version', 'e_entry', 'e_phoff', 'e_shoff',
    'e_flags', 'e_ehsize', 'e_phentsize', 'e_phnum', 'e_shentsize', 'e_shnum',
    'e_shstrndx'
);

[...]

sub parse_ehdr {
    my @hdr = ru($efh, "C a a a C C C C C x7 S S I q q q I S S S S S S", 0x40);
    mk_hash(\%ehdr, \@e_keys, \@hdr);
}
--------------------------------------------------------------------------------

In this case the ELF header is stored in %ehdr and its values can be accessed
by using their corresponding field names (e.g. $ehdr{'ei_mag0'}).

The program header table information is not used throughout the parsing and
mapping processes and therefore is skipped. Next, the section header table is
read and parsed as follows:

--------------------------------------------------------------------------------
 sub parse_shtab {
     seek $efh, $ehdr{'e_shoff'}, "SEEK_SET";
     for (my $i = 0; $i < $ehdr{'e_shnum'}; $i++) {
         my %sh;
         my @hdr = ru($efh, "I I q q q q I I q q", $ehdr{'e_shentsize'});
         mk_hash(\%sh, \@sh_keys, \@hdr);
         push @shtab, \%sh;

         # read content of section header entry of type 'STRTAB'
         if($sh{'sh_type'} == 3) {
             my $tmpstr;
             my $curr_offset = tell $efh;
             seek $efh, $sh{'sh_offset'}, "SEEK_SET";
             read $efh, $tmpstr, $sh{'sh_size'};
             seek $efh, $curr_offset, "SEEK_SET";
             $strtab{$sh{'sh_offset'}} = $tmpstr;
         }
     }
 }
--------------------------------------------------------------------------------

In the above code La table des en-têtes de section est représentée par le tableau @shtab
et ses entrées sont représentées sous forme de hachages based on the field names defined in
the @sh_keys array.

De plus, lorsqu'une entrée de la table des en-têtes de section de sh_type = 3 (STRTAB) est
trouvée, la position du filehandle $efh est définie sur son sh_offset pour la lecture du
contenu de l'entrée et le stocker dans %strtab, the hash that represents the string
table.

La table des en-têtes de section est analysée une seconde fois pour récupérer le
nom de chaque entrée basé sur le contenu de la table de chaînes. Les index pour le texte, les données,
symtab, rodata et rela.text (dans @shtab) sont stockés pour un accès direct
à ces sections plus tard dans les processus d'analyse et de cartographie.

--------------------------------------------------------------------------------
 sub secname {
     my $ndx = shift;
     my $str = shift;

     my $s = substr($str, $ndx);
     my $r = substr($s, 0, index($s, "\0"));

 # parse section names from string table
 sub parse_secnames {
     my $shstrtab = $shtab[$ehdr{'e_shstrndx'}];
     for(my $i = 0; $i < $ehdr{'e_shnum'}; $i++) {
         my $name = secname(
             $shtab[$i]{'sh_name'},
             $strtab{$shstrtab->{'sh_offset'}}
         );
         # add 'name' to each section header entry
         $shtab[$i]{'name'} = $name;

         # save indexes for easier access to relevant segments
         $text_ndx       = $i if($name eq '.text');
         $data_ndx       = $i if($name eq '.data');
         $symtab_ndx     = $i if($name eq '.symtab');
         $rodata_ndx     = $i if($name eq '.rodata');
         $relatext_ndx   = $i if($name eq '.rela.text');
     }
 }
--------------------------------------------------------------------------------

Ensuite, la table des symboles est lue et analysée comme suit :

The symbol table is represented by the @symtab array and its entries are
represented as hashes based on the field names defined in the @st_keys array,
with an extra field "name" that represents the symbol's name obtained from the
string table. De plus, the %funcs hash is used to store the st_value of
a function based on its name.

Relocations are read and parsed in a similar way:

--------------------------------------------------------------------------------
 # parse relocations

 my $entry_num = $rt->{'sh_size'}/$rt->{'sh_entsize'};
 [..]
 for (my $i = 0; $i < $entry_num; $i++) {
     my %r;
     my @hdr = ru($efh, "q Q i", $rt->{'sh_entsize'});
     mk_hash(\%r, \@r_keys, \@hdr);

     # 4 bytes on little endian order
     my $sym_ndx = unpack("V", pack("N", $r{'r_info'} >> 8));
     # low-order bits only
     my $type = $r{'r_info'} & 0x0f;
     my $sym_name = $symtab[$sym_ndx]{'name'};
     my $sym_shndx = $symtab[$sym_ndx]{'st_shndx'};

     $r{'symndx'} = $sym_ndx;
     push @relocs, \%r;

     # the num_extsym counter is used later for lookup in a 'jump table'
     $extsym{$sym_name} = $num_extsym++ if($sym_shndx == 0);
 }
--------------------------------------------------------------------------------

In this case, the relocations are represented by the @relocs array and its
entries are represented as hashes based on the field names defined in the
@r_keys array, with two extra fields "type" and "symndx" that represent the
relocation type and the index in the symbol table of the symbol associated to
the relocation entry. The hash %extsym is used as well to keep track of the
number of external symbols and their names.

Enfin, parse_elf() subroutine is defined as follows:

     my $fh = shift;
     $efh = $fh;

     parse_ehdr();
     parse_shtab();
     parse_secnames();
     parse_symtab();
     parse_relocs();
 }

====[ partie 3 : mapper ELF ]=========================================================

La majeure partie du processus de cartographie est basée sur [9] qui se compose essentiellement de trois
étapes :

   i) Cartographie mémoire
  ii) Copie de données dans la zone mappée
 iii) Protection d'accès mémoire


i) Cartographie mémoire

Cartographie mémoire can be achieved by using Perl's appel système() to call mmap:

--------------------------------------------------------------------------------
 my $ptr = appel système(9, $addr, $size, $protect, $flags, -1, 0);
--------------------------------------------------------------------------------

Où :

 - 9 est le numéro de l'appel système mmap sous Linux x86_64.

 - $addr est l'adresse de départ pour le nouvelle cartographie. If 0, mmap will choose a
   suitable address and return it.

 - $size est la taille de la cartographie.

 - $protect est un entier qui indique la protection mémoire de la cartographie.
   Les valeurs possibles peuvent être vérifiées à [10]. Dans ce cas, la valeur
   PROT_READ | PROT_WRITE = 3 est utilisée.

 - $flags est un entier qui indique la visibilité des changements de cartographie et l'utilisation de
   fichiers. Dans ce cas, la valeur MAP_SHARED | MAP_ANONYMOUS = 33 est utilisée.

Les paramètres restants sont liés à la cartographie de fichiers et peuvent être ignorés en utilisant
les valeurs -1 et 0.

mmap will return the starting address of the mapped area on success and -1 on
failure.


ii) Copie de données dans la zone mappée

Contrairement à mmap, il n'y a pas d'appel système pour copier des données en mémoire. There is also no
built-in function in Perl for copying raw data into mémoire. However, there are
some mémoire tricks that can be used to that end: peek & poke.

The code used for peek & poke is from [11], a script for appel système/shellcode
de appel système/shellcode sous OSX, qui permet de copier des données arbitraires $bytes dans une mémoire
adresse $location de choix.

(NOTE : certains commentaires et vérifications ont été supprimés pour simplifier ; the remaining
comments are from the original author)

--------------------------------------------------------------------------------
sub _pack_address {
  my $p = pack("Q", $_[0]);
  return $p;
}

sub peek {
  unpack "P$_[1]", _pack_address($_[0]);
}

sub poke {
  my($location, $bytes) = @_;

  my $len = length($bytes);
  my $addr = _pack_address($location);

  # construct a B::PV object, backed by a SV/SvPV to a dummy string
  # length($bytes) long, and substitute $location as the actual string storage
  # we specifically use the same length so we do not have to deal with resizing
  my $dummy = 'X' x $len;
  my $dummy_addr = \$dummy + 0;
  my $ghost_sv_contents = peek($dummy_addr, 8 + 4 + 4 + $Config{ivsize});
  substr( $ghost_sv_contents, 8 + 4 + 4, 8 ) = $addr;

  my $ghost_string_ref = bless( \ unpack(
    "Q",
    # it is crucial to create a copy of $sv_contents, and work with a temporary
    # mémoire location. Otherwise perl mémoire allocation will kick in and wreak
    # considerable havoc culminating with an inevitable segfault
    do { no warnings 'pack'; pack( 'P', $ghost_sv_contents.'' ) },
  ), 'B::PV' )->object_2svref;

  # now when we write to the newly created "string" we are actually writing
  # to $location
  eval 'substr($$ghost_string_ref, 0, $len) = $bytes';
  return $len;
}
--------------------------------------------------------------------------------

En bref, poke() modifie les types de données internes de Perl pour forcer la création d'une
variable temporaire pointant vers une chaîne située à $location puis change
le contenu de la chaîne avec $bytes. To have a better understanding of how poke()
works it's necessary to dig deeper into advanced concepts of Perl internals,
which is beyond the scope of this  article. The reader can check [12][13] for
more information.


iii) Protection d'accès mémoire

Similaire à la cartographie mémoire, appel système() de Perl est utilisé pour appeler mprotect :

--------------------------------------------------------------------------------
 my $mp = appel système(10, $addr, $size, $protect);
--------------------------------------------------------------------------------

Où :

 - 10 est le numéro de l'appel système mprotect sous Linux x86_64.

 - $addr et $size définissent l'intervalle de la zone mappée où les protections
    d'accès seront mises à jour.

 - $protect est un entier qui indique la protection mémoire[14] pour the
   specified interval. Dans ce cas, la valeurs PROT_READ | PROT_EXEC = 5 and
   PROT_READ = 1 are used.

mprotect retournera 0 en cas de réussite et -1 en cas d'échec.

Le processus de cartographie peut maintenant être effectué en suivant les étapes décrites dans [9]. Premièrement,
le code de l'objet ELF est mappé et son contenu est copié dans la zone mappée.

--------------------------------------------------------------------------------
 $base_ptr = mmap(0, length($code), 3, 33);
 if($base_ptr == -1) {
     print "Failed to allocate mémoire for ELF\n";
     exit;
 }

 poke($base_ptr, $code, length($code));
--------------------------------------------------------------------------------

Ensuite, les segments texte, données et rodata sont mappés et copiés en mémoire
les uns à côté des autres, avec une table de saut auxiliaire (décrite plus tard). Given that
the $code variable is a string that contains the binary content of the ELF
object (as discussed in part 1), the content of each segment can be obtained by
extracting a substring of $code based on their sh_offset and sh_size values.

--------------------------------------------------------------------------------
 my $text    = $shtab[$text_ndx];
 my $data    = $shtab[$data_ndx];
 my $rodata  = $shtab[$rodata_ndx];

 my $jmptab_size = $num_extsym*14;

 my $text_ptr = mmap(
     0,
     page_align($text->{'sh_size'}) +
     page_align($data->{'sh_size'}) +
     page_align($rodata->{'sh_size'}) +
     page_align($jmptab_size),
     3,
     33
 );

 if ($text_ptr == -1) {
     print "Failed to allocate mémoire for .text\n";
     exit;
 }

 my $data_ptr   = $text_ptr + page_align($text->{'sh_size'});
 my $rodata_ptr = $data_ptr + page_align($data->{'sh_size'});
 my $jmptab_ptr = $rodata_ptr + page_align($rodata->{'sh_size'});

 # copy segments into mémoire
 poke(
     $text_ptr,
     substr($code, $text->{'sh_offset'}, $text->{'sh_size'})
 );
 poke(
     $data_ptr,
     substr($code, $data->{'sh_offset'}, $data->{'sh_size'})
 );
 poke(
     $rodata_ptr,
     substr($code, $rodata->{'sh_offset'}, $rodata->{'sh_size'})
 );
--------------------------------------------------------------------------------

Après cela, les réadressements sont appliqués et les protections d'accès mémoire sont
fixées pour le segment texte, le segment rodata et la table de saut.

--------------------------------------------------------------------------------
 do_relocs($text_ptr, $data_ptr, $rodata_ptr, $jmptab_ptr);

 if(mprotect($text_ptr, $text->{'sh_size'}, 5) == -1) {
     print "Failed to mprotect .text\n";
     exit;
 }

 # check .rodata sh_size fist in case is not defined
 if(exists $rodata->{'sh_size'}) {
     if(mprotect($rodata_ptr, $rodata->{'sh_size'}, 1) == -1) {
         print "Failed to mprotect .rodata\n";
         exit;
     }
 }

 if(mprotect($jmptab_ptr, $jmptab_size, 5) == -1) {
     print "Failed to mprotect jump table\n";
     exit;
 }
--------------------------------------------------------------------------------


====[ partie 4 : réadressements et symboles externes ]================================

Similaire au processus de cartographie, les réadressements sont effectués en suivant les étapes
décrites dans [15] qui ne considère que des réadressements de type R_X86_64_PLT32 = 4
et R_X86_64_PC32 = 2 pour les segments texte, données et rodata. Une fois de plus, the
use of poke() allows copying the calculated relocation address into the original
patch offset address.

--------------------------------------------------------------------------------
 my $sym_ndx = $relocs[$i]{'symndx'};

 [...]

 my $patch_offset = $text_ptr + $relocs[$i]{'r_offset'};

 $base_ptr = $text_ptr if($sec_name eq '.text');
 $base_ptr = $data_ptr if($sec_name eq '.data');
 $base_ptr = $rodata_ptr if($sec_name eq '.rodata');

 $sym_addr = $base_ptr + $symtab[$sym_ndx]{'st_value'};

 [...]

 if($relocs[$i]{'type'} == 4 or $relocs[$i]{'type'} == 2) {
     my $relo = $sym_addr + $relocs[$i]{'r_addend'} - $patch_offset;
     # pack in little endian order (4 bytes)
     $relo = pack("V", $relo);
     # apply relocation by simply copying the calculated address
     # into the patch offset address
     poke($patch_offset, $relo, length($relo));
 }
--------------------------------------------------------------------------------

Symboles externes, identifiés par st_shndx = 0 (UND), are handled during
the relocation process following the steps described in [16]. Pour réaliser cela, a
simplified PLT/GOT is implemented by using an auxiliary jump table to resolve
les références externes. Chaque entrée de la table de saut contient :

 - L'adresse du symbole externe (8 octets).
 - Une instruction de saut fixe "\xff\x25\xf2\xff\xff\xff" (6 octets).

Pour plus de simplicité, the jump table is implemented by mapping N*14 bytes after the
rodata segment et chaque entrée de la table de saut commence à la position i*14, where
'N' is the number of external symbols and 'i' is a value between 0 and N-1 that
représente le i-ème symbole externe trouvé pendant le processus d'analyse.

--------------------------------------------------------------------------------
 sub map_elf {

         page_align($jmptab_size),

         33

     [...]

     my $jmptab_ptr = $rodata_ptr + page_align($rodata->{'sh_size'});

     [...]

 }

Étant donné que la table de saut est assez proche en mémoire du reste des sections,
le réadressage pour un symbole externe doit être calculé par rapport à l'instruction de saut fixe
dans son entrée de la table de saut, which performs a backwards jump (-14
bytes) to the start of the entry, where the actual address of the external
symbol is stored.

--------------------------------------------------------------------------------
 my $sym_ndx = $relocs[$i]{'symndx'};

 [...]

 my $sym_name = $symtab[$sym_ndx]{'name'};

 [...]

 my $jmptab_ndx = $jmptab_ptr + ($extsym{$sym_name}*14);
 $sym_addr = $jmptab_ndx + 8;
--------------------------------------------------------------------------------

L'adresse du symbole externe peut être obtenue en utilisant le module standard DynaLoader de Perl qui
« charge dynamiquement les bibliothèques C dans le code Perl »[17]. Premièrement, a library
reference for looking up the symbol must be loaded with dl_load_file(). In this
case the glibc shared object is used:

--------------------------------------------------------------------------------
 my $libc_path = "/usr/lib/x86_64-linux-gnu/libc.so.6";
 my $libref = DynaLoader::dl_load_file($libc_path, 0x01);
--------------------------------------------------------------------------------

L'adresse du symbole externe est recherchée à l'aide de dl_find_symbol() avec la bibliothèque
de référence et le nom du symbole en tant que paramètres. The jump table entry is then
built by packing the external address in little-endian order and appending the
jump instruction. Enfin, the jump table entry is copied into mémoire at the
position $jmptab_ndx calculated before. Après cela, le processus de relocalisation est
relogé en utilisant $jmptab_ndx + 8 comme adresse de symbole pour la formule de relocalisation.

--------------------------------------------------------------------------------
 my $jmptab_ndx = $jmptab_ptr + ($extsym{$sym_name}*14);
 $sym_addr = $jmptab_ndx + 8;

 [...]

 my $ext_addr = DynaLoader::dl_find_symbol($libref, $sym_name);

 # "V" format is 4 bytes; external address is 8 bytes
 my ($p1, $p2) = unpack("V2", pack("Q", $ext_addr));
 my $jmptab_entry = pack("V", $p1);
 $jmptab_entry .= pack("V", $p2);
 $jmptab_entry .= "\xff\x25\xf2\xff\xff\xff";

 # update 'jump table' in mémoire
 poke($jmptab_ndx, $jmptab_entry, length($jmptab_entry));

 [...]
 my $relo = $sym_addr + $relocs[$i]{'r_addend'} - $patch_offset;

====[ partie 5 : exécuter ELF ]=====================================================

Le module standard DynaLoader de Perl est utilisé à nouveau pour exécuter les
fonctions mappées ELF. En plus du chargement de bibliothèques externes et de la recherche de symboles,
DynaLoader peut installer des « sous-routines externes » en utilisant dl_install_xsub () :

--------------------------------------------------------------------------------
 my $ref = dl_install_xsub($perl_name, $symref [, $filename])
--------------------------------------------------------------------------------

Cette méthode crée une nouvelle sous-routine externe Perl nommée $perl_name en utilisant
$symref comme pointeur vers la fonction qui implémente la routine. En cas de réussite,
dl_install_xsub() retourne une référence à la « fonction installée ». According to
the DynaLoader documentation:

"Il faut souligner que DynaLoader, par lui-même, est pratiquement inutile
pour accéder aux bibliothèques non-Perl car il fournit presque aucune
colle Perl-vers-C'.  There is, for example, no mechanism for calling a C library function
or supplying arguments"

However, it is possible to use dl_install_xsub() providing the st_value of an
ELF's mapped function as pointer and successfully achieve exécution.

--------------------------------------------------------------------------------
sub exec_func {
    my $func_name   = shift;
    my $text_ptr    = shift;
    my $func_ptr    = $funcs{$func_name};

    my $func = DynaLoader::dl_install_xsub(
        "_japh", # not really used
        $text_ptr + $func_ptr,
        __FILE__ # no file
    );

    # dereference and execute
    &{$func};
}
--------------------------------------------------------------------------------

In this case the name of the function to be executed is "main". Enfin, the
main logic of the script can be reduced to:

--------------------------------------------------------------------------------
my ($code, $fh) = read_elf();
parse_elf($fh);
my $text_ptr = map_elf($code);
exec_func('main', $text_ptr);
--------------------------------------------------------------------------------

Et ensuite :

 $ perl exec_elf64.pl
 i am an elf
 japh
