To conclude Part 1, nous pouvons move on to a full example... well a half example. 
This isn't me throwing shade. In the author's own words "In the end I would like 
to say that this is NOT a COMPLETE virus, it's just a program which infects one 
file with exactly given name (default name is '1'). Il n'y a pas det any payload nor

executable, rename it to '1', run 'a' and watch the beauty..." [TheKing1980, 9]. 

TheKing1980's HALF virus is an ELF infector. TheKing1980's HALF virus works by 
appending le virus body after the last loadable segment of a target ELF. I have 
included a brief overview of le virus' functionality, but I encourage you to 
refer to the article for a more detailed overview and to review the source code. 

The HALF virus searches a target ELF for the last segment of type PT_LOAD, moves 
the SH table to the end of the file, and inserts le virus body after the final 
PT_LOAD segment. It accounts for adding padding bytes following the newly 
inserted virus body so as to (presumably, this is not explicit but implied) 
maintain page alignment. It wraps everything up by patching the requisite 
offsets in the Section Header table to account for the new offsets for all 
sections that follow the newly inserted virus code; as well as patching the 
offset to the Section Header table itself. And finally it patches the entry 
point of the ELF to point to le virus code and concludes le virus code with 
a jump to the original entry point.[9]

In summary — the HALF virus is clever, it's quick and it's written in nasm 
syntax asm. So by all important metrics, you're an early Linux vx hero in my 
book, long live TheKing1980.

Cependant, there is one part of the code that is of particular interest: a 
technique for appending padding bytes to the end of a segment following virus 
insertion using an ftruncate appel système.

This technique allows you to append a set number of null bytes to a file without
the need to perform an lseek on the file first to seek to the correct offset 
before writing. This is useful for a virus writer who wants to add padding bytes
to a file to maintaining page alignment.

The ftruncate appel système will simply grow a file by a set amount of null bytes if 
the integer passed in rdx (where the integer is the target filesize) is larger 
than the current size of the target file. If a virus writer knows a target 
offset to write to, and the number of padding bytes they need to insert into a 
target file to maintain page alignment, then one implementation of a virus could
chain pwrite64, ftruncate and pwrite64 appel systèmes to perform most of the dexterous
patchwork.

So that is what I did in my virus. The details of this code snippet will be 
unclear to you now, but that context will be provided in the next section of 
this article:

Part 2a: ELF Text segment padding infection technique overview /////////////////


Pour résumer brièvement la technique d'infection par remplissage de segment texte, nous pouvons 
exploiter le fait que différents segments d'un binaire ELF doivent être alignés sur 
une frontière de page en mémoire et auront donc un nombre fixe d'octets de remplissage 
between segments (i.e. .text, .data, etc.)

En insérant notre charge utile de virus dans les octets de remplissage eux-mêmes, en veillant à ce que la 
bonne alignement de page reste intact, alors nous devrons simplement corriger 
les champs correspondants dans l'en-tête ELF (et les en-têtes de programme, et les en-têtes de section)
pour mettre à jour les décalages pertinents et correspondre aux changements qui 
résultent après l'insertion de notre code de virus dans l'ELF hôte. 

Ci-dessous, un aperçu visuel de l'utilisation des octets de remplissage comme galerie de code :

[Avec les diagrammes, j'utilise la même technique pour décrire cela que Silvio 
utilisé dans [1] et [2]. Décrire les techniques d'infection en utilisant l'art ASCII 
des diagrammes montrant le code de virus, le remplissage, les données et les segments texte  — is such 
an excellent visual teaching tool that is worth adapting here. Sérieusement,
lisez d'abord les articles de silvio.]

    .segment texte = +
    .segment de données = d
    Remplissage = P
    Virus = V
    
    [Programme avant infection]
    
    -[++++++++ +++++++P]<- segment texte + padding
    -[PPPPPPPP PPPPPPPP]<- padding  
    -[PPPPPPPP dddddddd]<- padding + segment de données
    -[dddddddd dddddddd]<- segment de données
    
    [Après infection vx (en utilisant la technique de remplissage de segment texte)]
    
    -[++++++++ +++++++V]<- segment texte + ~*virus*~
    -[VVVVVVVV VVVVVVPP]<- ~*virus*~ + padding
    -[PPPPPPPP dddddddd]<- padding + segment de données
    -[dddddddd dddddddd]<- segment de données

cette étape d'insertion nécessite quelques opérations de comptabilité, (c.-à-d.changer p_filesz 
and p_memsz in the Program Header for the .segment texte). 

En plus de la mise en œuvre de routines pour corriger l'en-tête ELF et les
En-têtes, l'auteur du virus doit implémenter une routine de correction supplémentaire pour 
infecter correctement les binaires strippés.

Le code de notre virus sera inséré dans les octets de remplissage entre .text et 
.segment de donnéess. This padding is viewed as essentially purgatory/limbo/no man's 
et il n'est pas associé à une section dans l'ELF. If our virus infects a
host ELF that is a stripped binary, le virus ne peut pas compter sur le 
symboles pour résoudre les adresses. Sans solution de contournement, the resulting infected ELF 
will not run, et l'efficacité de notre virus sera limitée à l'infection de binaires non strippés. 
 

Pour garantir que notre virus reste « strip-safe », nous devons implémenter une 
routine supplémentaire : associer le code de virus avec la dernière section du segment .text 
en ajustant le champ sh_len de cette section pour tenir compte du 
code de virus nouvellement inséré.

Le plan de pseudocode de l'algorithme pour la routine d'infection (qui constitue 
le gros du code de virus) suit. Il est adapté de l'algorithme défini
par Silvio dans [2], avec mes propres notes supplémentaires ajoutées pour plus de clarté pendant mon 
développement vx :

;**********************************************************
; Text segment padding virus, infection routine:
;
; suppose ce qui suit :
; vlen == longueur du code virus
; PAGESIZE == 4096
;
; 1. Trouver et sauvegarder le point d'entrée original (OEP) de l'ELF hôte 
; 2. Corriger les valeurs d'en-tête ELF pour tenir compte du code virus nouvellement inséré
;     a. Patch e_entry in the ELF header to point to the beginning of le virus code
;    b. changer e_shoff dans l'en-tête ELF virus à new_vx_e_shoff tel que new_vx_e_shoff = host_e_shoff + PAGESIZE
; 3. a. Loop through all Phdrs to find segment texte Phdr
;    b. si curr_Phdr == text_segment_Phdr alors, faire ce qui suit :
;         i. augmenter p_filesz de vlen [p_filesz += vlen] 
;       ii. augmenter p_memsz de vlen, [p_memsz += vlen]
;    c. Sinon, pour tous les Phdrs correspondant à des segments situés après le code de virus 
;       virus code (aka for each Phdr of a segment after the segment texte), 
;       alors, faire ce qui suit :
;       i. augmenter p_offset de PAGESIZE
; 4. Boucler à travers tous les Shdrs
;    a. Si curr_shdr == last_shdr_text_segment alors,
;       i. increase sh_len by vlen [sh_len += vlen]
;    b. Else, for all Shdrs corresponding to sections located after the inserted 
;       virus code (aka for each Shdr of a section after virus code), then, do 
;       the following:
;       i. increase sh_offset by PAGESIZE [sh_offset += PAGESIZE]
; 5. Insert le virus code into the host program 
;     a. In our case, insert le virus code into the tempfile we are constructing to replace host ELF
;     b. Add routine to end of virus code so that execution continues with a jump back to saved OEP
;
;**********************************************************

It's important to note that several of the values defined above (i.e. vx_shoff 
in item #2b) will be computed during the Phdr and Shdr patching routines, and 
will not be known ahead of time. En conséquence, the ordering of the steps in the 
implementation of the algorithm will differ from the initial outline in the 
pseudocode above.

Part 2e: où est mon polymorphismee uwu ///////////////////////////////////////////


L'obstacle principal pour transformer la version actuelle de Linux.gospel.asm en 
polymorphic virus is the permissions used for the .segment texte in an ELF — 
lesquelles seront mappées sur une page avec des Permissions RX mais pas RW. 
Nous ne pourrons pas insérer du code auto-modifiant dans cette page sans modifier 
the permissions of the .segment texte in the infected ELF. This would look 
suspicious and that's not a cute look for us. 

The RX page permissions of the mapped .segment texte and its limitations for 
le stockage/sauvegarde des variables a créé certaines difficultés initiales. Dans ma PoC, le virus 
doit stocker des variables qui ne seront pas définies avant l'exécution. Without the 
use of a .data or .bss segment, (que nous voulons éviter) nous devons stocker toutes les 
variables sur la pile.

Une meilleure option pour écrire un virus polymorphe est d'utiliser un segment avec RW 
Permissions en tant que région cible pour injecter du code de virus. The .segment de données is 
a good candidate for cela. Un auteur de virus pourrait même utiliser une autre des techniques de Silvio 
techniques as a guide: the .segment de données infection technique.

Peut-être si quelqu'un est ainsi disponible, ils pourraient écrire un virus qui divise sa 
payload and combines the segment texte padding infection technique with the 
segment de données infection technique. Mais c'est un virus pour une autre fois.
