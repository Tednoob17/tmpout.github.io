─ Introduction ───────────────────────────────────────────────────────────────

J'ai été en train de réfléchir à faire du fuzzing sur les projets qui prennent des binaires ELF en entrée
depuis que j'ai lu le blog de xcellerator "Dead Bytes"[0] dans tmpout #1. In his blog, he 
clearly demonstrates that some ELF and program headers are ignored by the 
loader. I took the inspiration from these corruptions and targeted the open 
source projects avec une seule balle d'argent, qui est le `dead_bytes.bin`. I 
wanted to prove the idea of "Linux loader is the least picky parsers among the
les outils Linux standard". I also decided to suggest a fix for every 
plantement I found in order to be more useful both for myself and for the les projets Python.
Cependant, étonnamment, même si je n'avais pas écrit de harnesses avancés (j'utilisais
juste argv, ce qui signifie une exécution plus lente par seconde), ce binaire hérétique 
et à peine valide "dead_bytes.bin" a pu causé des problèmes ! 
J'ai passé mon temps principalement en triage de plantements. Comme vous pouvez l'imaginer, after a while it 
started to get really exhausting. (Reaching out developers, checking how the 
project owner handles things, les noms acceptés, la CoC etc etc.) It may sound I 
have worked on thousand projects but no.

─ L'aventure commence ───────────────────────────────────────────────────────

En fait, commencer une simple campagne de fuzzing avec AFL++ est vraiment simple. 

Il faut deux choses ;

    1) Construire et instrumenter le projet avec la chaîne d'outils AFL++
    2) Trouver une fonction ou un binaire exemple qui est capable 
       de consommer et de gérer l'entrée mutée.

Vous pouvez demander, « Qu'est-ce que c'est que l'instrumentation ? ». Clarifions simplement cela !

L'instrumentation peut être expliquée comme un ajustement de blocs de code pour
augmenter la quantité de code testé par le fuzzer. The injected code allows fuzzers to get 
coverage information and which track code suivre les chemins de code exécutés. Instrumentation 
also helps to find more complex bugs, which is a problem if you do "brute-force 
fuzzing", (en mutant des octets aléatoirement (également connu sous le nom de "mode dumb")).

Ne vous laissez pas tromper par le terme "mode dumb". Avec seulement 30 lignes de code Python, 
so1den avait trouvé une vulnérabilité de déréférence de pointeur nul dans radare2[3]. The difference 
here is, la guidance et ces marqueurs de rétroaction grâce à l'instrumentation. 
La dernière chose à savoir, c'est que l'instrumentation est effectuée au moment de la compilation in 
the examples in this paper.

Maintenant que vous savez ce qu'est l'instrumentation, vous pouvez voir pourquoi le projet 
doit être construit avec AFL++. Ces deux choses suffisent pour un fuzzer primitif. At least, it 
will test some functions of the target while you are developing a much more 
advanced version of it. Prenons radare2 comme exemple et supposons que nous ne
sachions absolument rien du code, de la façon dont il est écrit, or how radare2 processes 
files. Les étapes sont ;

    1) $ git clone https://github.com/radareorg/radare2.git && cd radare2;
    2) $ CC=afl-gcc CXX=afl-c++ ./configure 
        (In Languages Tab: C 96.7% and C++ 0.7%)
    3) $ CC=afl-gcc CXX=afl-c++ make -j24 (wait till finish)
    4) $ afl-fuzz -i dir_to_sample_binaries/ -- binr/radare2/radare2 -qq -AA @@
        ...
        Then voila! Our campaign started!
    
Le fou rien, c'est que c'est ainsi que CVE-2023-1605 a été trouvé en 15 minutes avec a 
silver bullet! Après avoir compris ces étapes simples, vous pouvez faire un speedrun 
dans %ANY% catégories !  (new contest idea? idk heheh...)

─ Exemple de découverte ────────────────────────────────────────────────────────────

Le projet le plus intéressant pour moi était la bibliothèque d'analyse ELF sécurisée d'elfmaster. 
"libelfmaster"[4] a quelques vérifications de sécurité pour les en-têtes malveillants, and gives 
warnings about them. Les modes les plus intéressants sont ELF_LOAD_F_FORENSICS et
ELF_LOAD_F_STRICT (je l'appelle mode panic). 

I used `elfparse.c` example as a starting point and a harness and found plantementes
dans les deux modes. I find these plantementes valuable because I assume that the flags 
will be used by somebody doing forensics and that somebody SERIOUSLY does not 
want to be in trouble. 

J'ai donné "dead_bytes.bin" comme graine argentée, and the fuzzer could successfully mutate
it into something can pass these sanity checks and plantement the library. 

Par exemple, il y a une vérification pour des valeurs de table d'en-têtes in 
libelfmaster.c#2920[5]:

    if (elf_flags(obj, ELF_PHDRS_F) == true &&
        elf_type(obj) != ET_REL) {
        offset_len = obj->ehdr64->e_phoff +
            obj->ehdr64->e_phnum * sizeof(Elf64_Phdr);
        if (offset_len > obj->size) {
            elf_error_set(error, "unsafe phdr table value(s)");
            goto err;
        }
    }

Cela peut être expliqué comme suit ;

  1) Vérifie si le drapeau ELF_PHDRS_F est défini et que l'identifiant de
     fichier ELF n'est pas ET_REL (Fichier repositionnable)
  2) Calcule si e_phoff + ( e_phnum * sizeof(struct elf64 program header) )
     dépasse la taille réelle de l'objet 
  3) Si cela dépasse, aller à l'erreur.

Aussi, dans libelfmaster.c#2915[6], si e_phnum && e_phoff sont supérieurs à
zéro, ELF_PHDRS_F est défini.

Vous voyez déjà comment cette vérification peut être contournée ? L'entrée mutée qui
caused the plantement had the following attributes;

  1) e_phoff = 0 
  2) e_phnum était un entier supérieur à zéro.
  3) Le type était ET_EXEC (Fichier exécutable)

Cette entrée n'aura pas de drapeau ELF_PHDRS_F, donc elle n'atteindra pas
la vérification de sécurité offset_len > taille_actuelle sur la première ligne de l'extrait de code. 
Ensuite, cela mènera potentiellement à des mappages mémoire non valides et dangereux.  

─//─────────────────────────────────────────────────────────────────────────────
─ Vrai mutateur de dead bytes ────────────────────────────────────────────────────

Les découvertes jusqu'ici n'ont pas vraiment grand-chose à voir avec les xcellerator
found as dead. Nous avons besoin d'un vrai mutateur qui ne modifie que les octets morts. 
Grâce à AFL++, il permet aux utilisateurs d'écrire un mutateur personnalisé. To accomplish
this goal, I examined the examples in AFLplusplus' github repository[7]

J'ai pris le fichier example.c comme point de départ.

/*
   AFL++ Custom Mutator for LibGolf
   Written by @echel0n
   compile like this:
   gcc -O3 -fPIC -shared -o golf_mutator.so -I ~/AFLplusplus/include/ oof.c
 */
#include "libgolf.h"
#include "shellcode.h" 
#include "afl-fuzz.h" // <- it's at aflplusplus/include
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#define uchar unsigned char
#define DATA_SIZE 0x100

typedef struct my_mutator {
  afl_state_t *afl;
  size_t trim_size_current;
  int trimmming_steps;
  int cur_step;
  u8 *mutated_out, *post_process_buf, *trim_buf;
} my_mutator_t;

my_mutator_t *afl_custom_init(afl_state_t *afl, unsigned int seed) {
  srand(seed); // needed also by surgical_havoc_mutate()
  my_mutator_t *data = calloc(1, sizeof(my_mutator_t));
  if (!data) {
    perror("afl_custom_init alloc");
    return NULL;
  }
  if ((data->mutated_out = (u8 *)malloc(MAX_FILE)) == NULL) {
    perror("afl_custom_init malloc");
    return NULL;
  }
  if ((data->post_process_buf = (u8 *)malloc(MAX_FILE)) == NULL) {
    perror("afl_custom_init malloc");
    return NULL;
  }
  if ((data->trim_buf = (u8 *)malloc(MAX_FILE)) == NULL) {
    perror("afl_custom_init malloc");
    return NULL;
  }
  data->afl = afl;
  return data;
}

// literally copy-pasted those from example.c, nothing changed.

size_t afl_custom_fuzz(my_mutator_t *data, uint8_t *in_buf, size_t buf_size,
                       u8 **out_buf, uint8_t *add_buf,
                       size_t add_buf_size, // add_buf can be NULL
                       size_t max_size) {

  RawBinary elf_obj;                           // }  \
  RawBinary *elf = &elf_obj;                   // }   \
  elf->isa = 62;                               // }    \
  Elf64_Ehdr *ehdr;                            // }     -> INIT_ELF(X86_64, 64) MACRO
  Elf64_Phdr *phdr;                            // }    /     expanded for better 
  copy_text_segment(elf, buf, sizeof(buf));    // }   /      understanding
  ehdr = populate_ehdr(elf);                   // }  /
  phdr = populate_phdr(elf);                   // } /
  set_entry_point(elf);                        // }/
  
  size_t mutated_size = ehdr_size + phdr_size + elf->text.text_size;
  
  // let's put the mutated bytes into dead bytes.

  ehdr->e_ident[EI_CLASS] = (uint8_t *)(in_buf + pos);
  pos = pos + 1;
  ehdr->e_ident[EI_DATA] = (uint8_t *)(in_buf + pos);
  pos = pos + 1;
  ehdr->e_ident[EI_VERSION] = (uint8_t *)(in_buf + pos);
  pos = pos + 1;
  ehdr->e_ident[EI_OSABI] = (uint8_t *)(in_buf + pos);
  pos = pos + 1;
  for (int i = 0x8; i < 0x10; ++i) {
    (ehdr->e_ident)[i] = (uint8_t *)(in_buf + pos);
    pos = pos + 1;
  }

  ehdr->e_version = (uint32_t *)(in_buf + pos);
  pos = pos + 4;
  // sections headers
  ehdr->e_shoff = (uint64_t *)(in_buf + pos);
  pos = pos + 8;
  ehdr->e_shentsize = (uint16_t *)(in_buf + pos);
  pos = pos + 2;
  ehdr->e_shnum = (uint16_t *)(in_buf + pos);
  pos = pos + 2;
  ehdr->e_shstrndx = (uint16_t *)(in_buf + pos);
  pos = pos + 2;
  ehdr->e_flags = (uint32_t *)(in_buf + pos);
  pos = pos + 4;
  // physical addr
  phdr->p_paddr = (uint64_t *)(in_buf + pos);
  pos = pos + 8;
  phdr->p_align = (uint64_t *)(in_buf + pos);
  pos = pos + 8;

  /* let's mimic GEN_ELF()
   * Write:
   * - ELF Header
   * - Program Header
   * - Text Segment
   */

  memcpy(data->mutated_out, ehdr, ehdr_size);
  memcpy(data->mutated_out + ehdr_size, phdr, phdr_size);
  memcpy(data->mutated_out + ehdr_size + phdr_size, elf->text.text_segment,
         elf->text.text_size);

  *out_buf = data->mutated_out;
  return mutated_size;
}

void afl_custom_deinit(my_mutator_t *data) {
  free(data->post_process_buf);
  free(data->mutated_out);
  free(data->trim_buf);
  free(data);
}
