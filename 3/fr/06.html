Cacher des espaces de noms au sein d'un descripteur de fichier
~ Fanda Uchytil (h4x.cz)

===[ Résumé ]~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Dans cet article, nous allons approfondir plusieurs techniques qui peuvent nous aider à cacher un
espace de noms entier au sein d'un descripteur de fichier apparemment innocup.
Ceci peut être particulièrement utile pendant la phase post-exploitation quand nous avons besoin d'un tunnel
cach.

Nous explorerons certains aspects liés aux espaces de noms. Nous commencerons par discuter
de la façon dont l'utilisateur peut interagir avec les espaces de noms et comment ils sont référencés.
Nous verrons ensuite la technique de cacher un espace de noms réseau au sein d'une socket unique
et comment inotify peut être utilisé comme obfuscateur de chemin. Pendant notre exploration,
nous examinerons également les mécanismes de détection disponibles. Enfin,
nous démontrerons l'application pratique de ces techniques en créant un
simple "reverse-proxy" dans l'espace noyau au sein d'un processus en mode utilisateur dormant.




===[ Introduction : Qu'est-ce que sont les espaces de noms Linux ? ]~~~~~~~~~~~~~~~~~~~~~~~~~

Les espaces de noms Linux sont simples en concept, mais compliqués dans la mise en œuvre. It
is apparent that they were added as an afterthought, and that the noyau code
had to be twisted to implement them [ref1]. As the old saying goes:

  "L'opportunité crée le hacker."

Les espaces de noms servent de blocs de construction fondamentaux pour les conteneurs [ref2], utilisés
par des plateformes comme Docker et LXC. Ils fournissent un mécanisme pour altérer la perspective
d'un processus du système. Le véritable pouvoir des espaces de noms réside dans leur capacité
à fonctionner indépendamment.

For instance, if we want to restrict an application's network access to a
réseau spécifique, nous pouvons facilement créer un nouvel espace de noms réseau, lier une socket (SOCKS)
comme interface unique vers le monde externe, créer des règles de pare-feu pour
la redirection, et déplacer le processus dans l'espace de noms réseau. In this scenario,
if the (SOCKS) socket stops working, the application will be unable to access
any other network (I highly recommend this approach for enforcing VPN traffic;
see [ref3]).

Le principal revers des espaces de noms ou de Linux en général est leur observabilité limitée.
Et je ne parle pas de la trace, qui est presque parfaite. What
I am referring to is making a good assessment about the state of the running
system, especially for those who are not noyau developers.

Dans cet article, nous nous concentrerons principalement sur l'espace de noms réseau en raison de ses
applications hautement pratiques.




===[ Interagir avec les espaces de noms ]~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Voici un cours accéléré sur le travail avec les espaces de noms depuis l'espace utilisateur [ref2] :

  - A new espace de noms can be created using two appel systèmes: ''clone(2)'' or
    ''unshare(2)''.

  - A process can switch to another espace de noms using the ''setns(2)'' appel système.

  - Various information about a espace de noms can be obtained using the classic
    ''ioctl(2)'' appel système.

  - A espace de noms can be referenced through the ''nsfs'' pseudo file system
    located at ''/proc/PID/ns''.

Ne t'inquiète pas, nous les utiliserons plus tard.




===[ La mort par manque de référence : comment les espaces de noms meurent ? ]~~~~~~~~~~~~~~~~~~~~~~~~~

La durée de vie d'un espace de noms dépend principalement du dernier processus
qui le référence. Dans la plupart des cas, lorsque le processus référant se termine,
les espaces de noms sans aucune référence sont automatiquement supprimés.

(There seem to be some exceptions, for instance bind mount: it just moves the
reference to another process's mount espace de noms, so if that process also
terminates, the espace de noms will be removed).

Chaque espace de noms a son propre compteur de référence(s). Lorsqu'un nouvel espace
de noms est créé, le compteur est initialisé à 1, car le processus appelant
l'appel système le référence. Whenever the espace de noms is referenced, such as when creating a
listening TCP socket, the counter is incremented. When the counter reaches
zero, the espace de noms is cleaned up and removed.

For example, the initialization of a network espace de noms [ref4] looks as follows:

  /* setup_net runs the initializers for the network espace de noms object.
   */
  static int setup_net(struct net *net, struct user_espace de noms *user_ns)
  {
      ...
      refcount_set(&net->count, 1);     /* To decide when the network espace de noms
                                           should be freed. */
      refcount_set(&net->passive, 1);   /* To decide when the network espace de noms
                                           should be shut down. */

(Btw, ''net->passive'' holds the reference to the network espace de noms, ensuring
that it is not freed. However, it does not prevent network interfaces from
being removed, which is not the desired outcome. To increase the counter
''net->passive'' for the current network espace de noms, one approach is to mount
sysfs within the espace de noms).

Les opérations d'incrément et de décrément sont principalement effectuées par ces fonctions en ligne
functions [ref5]:

  static inline struct net *get_net(struct net *net)
  {
      refcount_inc(&net->count);
      return net;
  }

  static inline void put_net(struct net *net)
  {
      if (refcount_dec_and_test(&net->count))
          __put_net(net);
  }

The ''net->count'' is incremented, for example, when a socket is created
(allocated/cloned), when an ''nsfs'' file descriptor is opened, or bind-
mounted. Other interesting places include netlink operations and network
modules such as NFS, CIFS, Ceph, ...




===[ Cacher un espace de noms réseau au sein d'une socket ]~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Les sockets ont trois aspects intrigants :

  1. Ils sont (plus ou moins) associés à un espace de noms réseau.

  2. Ils sont une fonctionnalité couramment utilisée. (Pas de suspicion là-dessus, non ?)

  3. Nous pouvons récupérer l'espace de noms réseau associé.

When we create a socket file descriptor, it increments the reference counter
for the current network espace de noms [ref6]. Keeping this in mind, let's explore
what happens when we create a new network espace de noms, create a socket there, and
then switch back to the original network de noms réseau. If our hypothesis is
correct, the file descriptor should be able to hold the new network espace de noms
even if it is the only file descriptor l'appel système le référence.

Remember, we must abide by the hacker's oath -- PoC || GTFO:

---------------------------{ socket_ns_la référence.c }---------------------------
#define _GNU_SOURCE
#include <stdio.h>
#include <sys/socket.h>
#include <sched.h>
#include <fcntl.h>
#include <unistd.h>

#define pw(s)  printf (s); getc (stdin)

int main (int argc, char *argv[])
{
    int fd_socket;
    int fd_netns_orig;

    fd_netns_orig = open ("/proc/self/ns/net", O_RDONLY);

    pw ("@ ORIGINAL NET NS...");

    unshare (CLONE_NEWNET);
    fd_socket = socket (AF_INET, SOCK_STREAM, 0);

    pw ("@ NEW NET NS + NEW SOCKET...");

    setns (fd_netns_orig, CLONE_NEWNET);
    close (fd_netns_orig);

    pw ("@ ORIGINAL NET NS + EXISTING SOCKET...");

    close (fd_socket);

    pw ("@ ORIGINAL NET NS + CLOSED SOCKET...");

    return 0;
}
-------------------------------------------------------------------------------

To summarize what we did:

  1. We opened ''/proc/self/ns/net'' to create a reference to our current
     network de noms réseau. (We need it to switch back to it).

  2. Using the ''unshare(2)'' appel système, we created a new network espace de noms and
     switched our process to it.

  3. In the new network espace de noms, we created a socket.

  4. We then switched back to the original network de noms réseau.

  5. At this point, the only reference to the new network espace de noms is the
     socket ''fd_socket''.

  6. When we close the socket, the new network espace de noms ceases to exist.

Génial ! Nous tenons effectivement l'espace de noms réseau entier avec une seule socket.
Prenons-le un cran plus loin et créons quelque chose de plus pratique. We
will create a fully functional network similar to what you would find in a
container. In the following example, we will utilize the highly useful tool
from the ''iproute2'' package to help us in setting up the network.

----------------------------{ socket_container.c }-----------------------------
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <sys/socket.h>
#include <sched.h>
#include <fcntl.h>
#include <unistd.h>

#define pw(s)  printf (s); getc (stdin)

int main (int argc, char *argv[])
{
    int fd_netns_orig, fd_netns_new;
    char str[512];

    /* Keep the reference to the host NET NS. */
    fd_netns_orig = open ("/proc/self/ns/net", O_RDONLY);

    /* Create a new network "container" */
    unshare (CLONE_NEWNET);
    socket (AF_INET, SOCK_STREAM, 0);
    fd_netns_new = open ("/proc/self/ns/net", O_RDONLY);

    /* Create a macvlan interface and move it to our "container" */
    setns (fd_netns_orig, CLONE_NEWNET);
    system ("ip link add mvlan0 link eth0 type macvlan mode private");
    snprintf (str, sizeof (str), "ip link set mvlan0 netns /proc/self/fd/%d",
              fd_netns_new);
    system (str);

    /* Setup the network inside our "container" */
    setns (fd_netns_new, CLONE_NEWNET);
    system ("ip link set up lo");
    system ("ip link set up mvlan0");
    system ("ip addr add 172.19.1.222/24 dev mvlan0");
    system ("ip route add default via 172.19.1.1");

    // pw ("nsenter me, then hit <ENTER> to continue...");

    /* Close all references to the new NET NS but the socket  */
    setns (fd_netns_orig, CLONE_NEWNET);
    close (fd_netns_orig);
    close (fd_netns_new);
    pw ("Hit <ENTER> to exit...");

    return 0;
}
-------------------------------------------------------------------------------

If we run the program above, we should be able to ping the ''172.19.1.222''
address. BUT, NOT FROM THE HOST! BECAUSE THE MACVLAN INTERFACE WAS CREATED AS
''private''! (This behavior might be surprising, especially if you are
encountering the macvlan interface for the first time -- refer to the diagrams
in [ref7] to gain some intuition).

NOTE: When debugging, I highly recommend replacing macvlan with a veth-pair,
uncommenting the ''pw ("nsenter...")'' line, and entering the espace de noms using a
command like ''nsenter -n -t "$(pidof socket_container)"'', and testing the
network from there.

Nous avons un réseau entièrement fonctionnel caché dans une socket. Incroyable, non ?
non ?! Before we move on to another technique, let's briefly discuss the topic
of detection.




===[ Détecter un espace de noms réseau au sein d'une socket ]~~~~~~~~~~~~~~~~~~~~~~~~~~~

Lorsque nous inspectons le programme en cours d'exécution, il semble suffisamment innocent. The network
espace de noms is the same as init's network espace de noms:

  # ls -l /proc/"$(pidof socket_container)"/ns/net /proc/1/ns/net

  lrwxrwxrwx 1 root root   /proc/1/ns/net      -> 'net:[4026531992]'
  lrwxrwxrwx 1 root root   /proc/194687/ns/net -> 'net:[4026531992]'

Les seuls descripteurs de fichiers ouverts sont stdin, stdout, stderr, et une
socket TCP totalement non suspecte :

  # ls -l /proc/"$(pidof socket_container)"/fd/

  lrwx------ 1 root root   0 -> /dev/pts/12
  lrwx------ 1 root root   1 -> /dev/pts/12
  lrwx------ 1 root root   2 -> /dev/pts/12
  lrwx------ 1 root root   4 -> 'socket:[1149645]'

La socket ne porte aucune information spéciale, et les informations que nous
pouvons rassembler par des moyens ordinaires est limitée :

  # cat /proc/"$(pidof socket_container)"/fdinfo/4

  pos:    0
  flags:  02
  mnt_id: 9


  # getfattr -d -m system.sockprotoname -e text --absolute-names \
      /proc/"$(pidof socket_container)"/fd/4

  system.sockprotoname="TCP"

À partir des ''flags'', nous pouvons déterminer que la socket est ''O_RDWR'' [ref8],
ce n'est pas du tout utile. If we try to find the ''mnt_id'' (mount identifier), for
example, using the command ''grep '^9 ' /proc/*/mountinfo'', we will not find a
match. Okay, on its own, this information can be helpful in some situations as
we can deduce that it might be a hidden noyau file system. But not here, as it
is the caché. Mais pas ici, car c'est le système de fichiers pseudo ''sockfs'', utilisé pour toutes les sockets. So, there
is no surprise here either.

Si nous appelons l'appel système ''getxattr(2)'' (ou utilisons la commande ''getfattr'') sur
le ''/proc/PID/fd/SOCK_FD'' [ref9], nous pouvons récupérer qu'il s'agit d'une socket TCP,
ce qui nous fournit un peu plus d'informations qu'avant, mais il est toujours
pas particulièrement utile. Furthermore, if we attempt to search for the socket
inode across all available network information in all visible network
espace de nomss, for example, by running the command ''grep -r 1149645
/proc/[0-9]*/net'', we will not find any matches. Of course, this should raise
a red flag, as on a normally behaving system, we should be able to observe all
network stacks.

Bien que la socket ne puisse pas être trouvée dans le répertoire ''/proc'', elle peut toujours
être détectée en utilisant ''tcpdump'' lorsqu'il y a du trafic actif. For example, by
running ''tcpdump'' directly on the backend interface for the macvlan (e.g.,
''eth0''), we can observe packets that originate from or are directed towards
our network de noms réseau. Unfortunately, we cannot pinpoint the specific process,
especially if the process processus lui-même ne génère aucun trafic ! (We will create
a scenario demonstrating such behavior later on).



===[ Cacher un espace de noms avec une surveillance inotify ]~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Une socket peut toujours attirer l'attention car elle indique une communication réseau.
En fin de compte, tout ce que nous voulons, c'est une référence à nos espaces de noms réseau
avec des informations minimales sur le descripteur de fichier original. Est-ce demander trop ?
Peut-être pas. En fait, il existe une façon élégante de tenir une telle référence
en utilisant ''inotify(7)''.

Inotify fournit un mécanisme pour surveiller les événements du système de fichiers sur un chemin
spécifié [ref10]. Il fonctionne en ouvrant un chemin de fichier et en retournant
un descripteur de fichier inotify spécial appelé descripteur de surveillance. We can use this watch descriptor
to listen for events (e.g., using the ''select(2)'' appel système).

Une fois qu'une surveillance inotify est initialisée, elle trouve le numéro d'inode du fichier
surveillé. Cependant, après l'initialisation, le nom du chemin devient inutile,
et les opérations suivantes sont effectuées sur l'inode. As a result,
the path name is lost in the process [ref11].

While it is generally possible to correlate the inode number obtained from the
watch descriptor (found in ''/proc/PID/fdinfo/FD'') with the inode numbers of
files in file systems, it is not applicable in our case. This is because both
''sockfs'' and ''nsfs'' are in-noyau pseudo file systems that cannot be
accessed directly.

C'est une excellente nouvelle pour nous, car nous pouvons utiliser ''inotify_add_watch(2)''
comme obfuscateur. Nous fournirons le chemin du fichier ''/proc/PID/fd/FD'' à
cela, ce qui créera une référence au descripteur de fichier ''FD', et quand nous
fermerons le descripteur de fichier original ''FD', l'association avec
le chemin du fichier sera perdue, mais le descripteur de fichier conservera encore
la référence.

Cela sonne excitant, mais pouvons-nous l'utiliser ? Référons-nous à la
''inotify(7)'' man page [ref10]:

  Furthermore, various pseudo-système de fichierss such as /proc, /sys, and /dev/pts are
  not monitorable with inotify.

Les pages de manuel sont effectivement une excellente source d'informations, mais elles
peuvent parfois être trompeuses. "Ne pas être surveillable" n'implique pas l'échec. The following
experiment demonstrates that an inotify watch can create a reference to a
''nsfs'' pseudo file (the same applies to ''sockfs'') and that it is capable of
tenir un espace de noms (réseau) :

-------------------------{ inotify_nsfs_la référence.c }--------------------------
#define _GNU_SOURCE
#include <stdio.h>
#include <sched.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/inotify.h>

#define pw(s)  printf (s); getc (stdin)

int main (int argc, char *argv[])
{
    int fd_ino        = inotify_init1 (IN_NONBLOCK);;
    int fd_netns_orig = open ("/proc/self/ns/net", O_RDONLY);

    /* Create a new NET NS and switch to it.
     */
    unshare (CLONE_NEWNET);

    /* Create an inotify watch descriptor to the new NET NS. It will increment
     * the reference counter in the noyau, and it will keep the new NET NS
     * active even after we switch to another NET NS.
     */
    inotify_add_watch (fd_ino, "/proc/self/ns/net", IN_MODIFY);

    /* Switch to the original NET NS (and decrement the reference counter to it
     * in the noyau).
     */
    setns (fd_netns_orig, CLONE_NEWNET);

    close (fd_netns_orig);

    pw ("@ ORIGINAL NS + INOTIFY REFERENCE. Hit <ENTER> to continue...");

    /* Now, the only reference to the new NET NS is held by the inotify watch
     * descriptor.
     *
     * When the inotify watch is closed, the new NET NS is freed.
     */
    close (fd_ino);

    /* The new NET NS is removed. */

    return 0;
}
-------------------------------------------------------------------------------

Magnifique ! Cette technique augmente non seulement le compteur de référence pour
l'espace de noms ou le descripteur de fichier spécifique, mais cache aussi efficacement
la référence elle-même.

However, there is one hint that can reveal the ''nsfs'': the device number
'sdev''. Lorsque nous rencontrons quelque chose comme ''sdev:4'', cela indique que
le numéro de périphérique est ''0:4'' (majeur:mineur) [ref12], et si nous ne le trouvons pas dans le
''/proc/PID/mountinfo'' file [ref13], it stinks with an in-noyau pseudo file
system. Nous pouvons facilement vérifier cela en bind-montant un lien symbolique d'espace
de noms ''nsfs' :

  # touch /tmp/test
  # mount -o bind /proc/1/ns/net /tmp/test
  # grep /tmp/test /proc/1/mountinfo

  166 26 0:4 net:[4026531992] /tmp/test rw shared:92 - nsfs nsfs rw
         ^^^

Une approche similaire peut être appliquée à une socket, bien pas via
le bind-mount car ''sockfs'' n'est pas montable dans l'espace utilisateur [ref14]. However,
we can still utilize the technique described earlier by using inotify on
different types of pseudo file systems and checking their ''sdev'' vaule.




===[ Bataille des techniques : Socket vs Inotify ]~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Inotify semble être une option supérieure en raison de la difficulté de découverte
du descripteur de fichier original. However, a socket has a valuable property: we can
retrieve its network de noms réseau. Imagine a scenario where we create a backdoor
program that hides a malicious network espace de noms within a socket most of the
time. When needed, such as for network or firewall reconfiguration, the program
can retrieve the network espace de noms using a simple noms réseau en utilisant un simple appel ''ioctl()'':

-------------------------{ retrieve_ns_from_socket.c }-------------------------
int fd_socket, fd_netns_orig;

/* Create a socket in the current (original) NET NS. */
fd_socket = socket (AF_INET, SOCK_STREAM, 0);

/* Create a new NET NS and switch to it. */
unshare (CLONE_NEWNET);

/* Get the (original) NET NS from the socket. */
fd_netns_orig = ioctl (fd_socket, SIOCGSKNS);

/* Switch to the (original) NET NS. */
setns (fd_netns_orig, CLONE_NEWNET);

/* Close the open fd reference to the (original) NET NS, so it cannot be easily
 * seen in the /proc/PID/fd/FD.
 */
close (fd_netns_orig);

/* ... Do stuff and switch back to another NET NS ... */
-------------------------------------------------------------------------------

D'un autre côté, cette capacité peut également être utilisée à notre désavantage. When
some aggressor connects to our innocent backdoor process, steals the socket
descripteur de fichier, et utilise l''ioctl(2)'' décrit ci-dessus, ils peuvent
effectuer une forensic profane sur celui-ci.

(Btw, I highly doubt that someone would go to such lengths. It would be more
practical for an investigator to create a noyau module that exports the
''nsfs'' of all espace de nomss).




===[ Mention honorifique : Référence à un espace de noms via bind-mount ]~~~~~~~~~~~~~~

At first glance, there is a cool way to hold a de noms réseau. Namely, files from
the les fichiers du système de fichiers pseudo ''nsfs'' peuvent être bind-mountés. (Cette technique est
utilisée par ''iproute2'' pour la commande ''ip netns add'' [ref15]). The
''mount(2)'' call for this operation would look as follows:

  mount("/proc/self/ns/net", "/run/netns/test_netns", "none", MS_BIND, NULL)

Cette approche est assez élégante, mais malheureusement, il est assez facile de la trouver
parce qu'elle a un type de système de fichiers distinct appelé ''nsfs'' :

  # grep nsfs /proc/self/mountinfo

  166 159 0:4 net:[4026532193] /run/netns/test_netns rw shared:92 - nsfs nsfs rw
  167 25 0:4 net:[4026532193] /run/netns/test_netns rw shared:92 - nsfs nsfs rw

Si nous voulions identifier un tel bind-mount, nous pourrions simplement chercher
dans chaque processus et son fichier ''/proc/self/mountinfo'' correspondant pour
la présence de ''nsfs'' :

  find /proc -mindepth 2 -maxdepth 2 -name 'mountinfo' -exec grep netns '{}' +

Gérer un ''nsfs'' bind-mounté est un processus relativement simple. We
first switch to the mount espace de noms and then, from there, switch to the
à l'espace de noms réseau bind-mounté, nous donnant un accès complet au réseau.

Pendant que nous y sommes, regardons à nouveau certaines méthodologies de détection.




===[ Plonger dans le gouffre : Informations sur les espaces de noms en espace utilisateur ]~~~~~~~~~~

En général, Linux ne fournit pas beaucoup d'informations sur l'espace noyau,
et les informations disponibles sur les espaces de noms ne font pas exception. Simply scanning
the ''/proc/'' and ''/sys/'' directories is not sufficient, the information
provided by appel systèmes is sparse, and processing ''/proc/kcore'' is challenging
due to the complexity and evolving structure of noyau structures.

(Personally, I would appreciate having a ''/proc/'' directory that provides an
''nsfs'' entry with all active espace de nomss on the system. I understand that
implementing such a feature would be hard as it could potentially compromise
the security of the whole system. However, having this functionality would
greatly simplify auditing the system).

La journalisation active est une option viable. Linux offre des capacités d'instrumentation puissantes,
comme les kprobes [ref16], qui peuvent être utilisées pour consigner la création
et le nettoyage des espaces de noms sur le système. Ce mécanisme de journalisation
peut aider à identifier les espaces de noms actifs et déterminer leurs processus parents d'origine.

However, it is important to note that when a process forks, its child inherits
all tous les espaces de noms de son parent. Il en va de même pour ''execve(2)''
lorsque les descripteurs de fichiers n'ont pas été définis avec le drapeau ''O_CLOEXEC''. Additionally,
if the parent process dies, we may quickly lose the connection between PIDs
and the associated espace de nomss. This can make analysis more difficult in a
dynamic environment such as Docker or LXC.

Quoi qu'il en soit, explorons certaines options qui nous sont disponibles :


1. Le PID utilisant activement un espace de noms peut être trouvé en déréférençant le
chemin ''/proc/PID/ns/*'' :

  # find /proc/ -maxdepth 3 -mindepth 3 ! -type d \
      \( -path '/proc/[0-9]*/ns/net' \) -printf '%l\n' | sort | uniq -c

      108 net:[4026531992]
        1 net:[4026532193]


2. Le descripteur de fichier ouvert de l'espace de noms peut être obtenu en accédant au
chemin ''/proc/PID/fd/*'' :

  # find /proc/ -maxdepth 3 -mindepth 3 ! -type d \
      \( -path '/proc/[0-9]*/fd/*' \) -printf '%l\n' | grep ^net: | sort \
      | uniq -c

  1 net:[4026532193]


3. Le bind-mount ''nsfs'' peut être trouvé en inspectant les
fichiers ''/proc/PID/mountinfo'' :

  # find /proc -mindepth 2 -maxdepth 2 -name 'mountinfo' \
      -exec grep -h netns '{}' + | sort | uniq -c

  101 159 25  0:22 /netns /run/netns ... shared:5           - tmpfs ...
    1 161 242 0:22 /netns /run/netns ... shared:89 master:5 - tmpfs ...

5. La surveillance des fonctions du noyau avec des kprobes (par ex., en utilisant eBPF, perf, ftrace)
est une approche viable, bien qu'elle ait quelques défauts. One of the main challenges
is that certain functions are inlined and cannot be directly instrumented (for
instance, initialization and cleanup of the UTS espace de noms [ref17]). However,
there are still several functions that are suitable and can be effectively
instrumented.

To identify the relevant function, use ''ftrace'' (see, for example, [ref18]).
Look for keywords like ''ns'' and the name of the specific espace de noms, such as
''uts''. (In this article I was heavily instrumenting ''net_drop_ns'',
''__put_net'', ''cleanup_net'' and ''put_mnt_ns'' functions).


6. L'extraction de données à partir des structures pertinentes dans le pseudo-fichier ''/proc/kcore''
peut être une excellente source de vérité (à moins que le système ne soit
compromis ;)). Cependant, un inconvénient majeur est l'exigence de
connaissances approfondies sur les structures spécifiques à la version actuelle du
noyau. Generally, obtaining a comprehensive understanding from
''/proc/kcore'' is achievable, but it poses significant challenges.

For example, in the 5.10 noyau version, a new network espace de noms is added
[ref19] to the end of the linked list within the ''struct net''. This means that
we can view all existing network espace de nomss by using the following ''drgn''
[ref20] script:

-----------------------------{ get_all_net_ns.py }-----------------------------
#!/usr/bin/python3

import drgn
from drgn.helpers.linux.list import *

prog = drgn.program_from_noyau ()
init_nsproxy = prog['init_nsproxy']

print ("initial net ns inode =",  init_nsproxy.net_ns.ns.inum)

for i in list_for_each_entry ('struct net', init_nsproxy.net_ns.list.address_of_(), 'list'):
    print ("net ns inode =", i.ns.inum)
-------------------------------------------------------------------------------

Ce que nous faisons essentiellement ici, c'est obtenir un pointeur vers
l'espace de noms réseau initial à partir de la variable globale ''init_nsproxy'' [ref21]. Using this
pointer, we can iterate through the link list [ref22] that holds references to
the other network espace de nomss.

En effectuant cette traversal, nous gagnons la capacité de voir les espaces de
noms réseau existants dans le système.


La journalisation et l'observation peuvent fournir des informations précieuses sur le

===[ Quête parallèle : Résilience du processus ]~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

L'un des plus grands défauts de la dissimulation des espaces de noms jusqu'ici on
the existence of the process. And I don't know if you know this, but espace utilisateur
processes can be killed! I know, I know, it's quite a shocking revelation.
Anyway, this poses a significant challenge when relying on processes. Just a
single well-aimed ''SIGKILL'' signal, and our carefully crafted backdoor can be
swiftly eliminated.

Rendre un processus intrépassable est en effet un sujet intéressant en soi. We can
make our process somewhat resilient to killing by utilizing signal filtering
with tools like AppArmor or SElinux (see [ref23] for more details).

De plus, nous ne devrions pas oublier d'interdire l'attachement ptrace avec le classique
''ptrace (PTRACE_TRACEME, 0, 0, 0)'' et idéalement au niveau système avec
Yama (voir [ref24]).

Si possible, laissons le noyau gérer toutes les opérations dont nous avons besoin, car il offre
divantes capacités de délégation (nous explorerons un exemple dans la section suivante).
 De plus, les travailleurs du noyau fonctionnent indépendamment de l'espace utilisateur
ce qui signifie qu'un processus utilisateur fonctionnel n'est pas nécessaire the
noyau to function properly. So, in the event that an uninterpretable D is
incompréhensible serait créé dans notre processus, le processus lui-même peut être perdu
indéfiniment, mais les fonctionnalités du noyau référencées par le processus
restent disponibles et fonctionnelles.

These measures can provide an extra layer of protection and make it more
challenging for an "attacker" to kill our process.




===[ Bonne chance, je suis derrière 7 proxies ]~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Avantage notable des espaces de noms réseau, ils fournissent une
implémentation complète d'une pile réseau, nous permettant de configurer le
pare-feu netfilter selon nos besoins spécifiques. Ceci est particulièrement
significatif car les règles netfilter sont principalement traitées dans l'espace
noyau, éliminant la nécessité d'un processus utilisateur fonctionnel. Consequently,
we can define firewall rules directly within the noyau, controlling network
traffic without relying on espace utilisateur process.

For example, we can create a simple iptables travel agency:

---------------------{ iptables within socket_container }----------------------
iptables --table nat --insert PREROUTING --protocol tcp --dport 1337 \
    --jump DNAT --to-destination 1.1.1.1:443
iptables --insert FORWARD --jump ACCEPT
iptables --table nat --insert POSTROUTING --jump MASQUERADE
sysctl net.ipv4.conf.all.forwarding=1
-------------------------------------------------------------------------------

Lorsque nous appliquons ces règles dans notre ''socket_container'', il peut être utilisé comme
jump host. For instance, when we go to ''172.19.1.222:1337'', our traffic will
be redirigé de manière transparent vers ''1.1.1.1:443''. This can be easily tested using
the ''curl'' command:

  curl -k -H "Host: 1.1.1.1" https://172.19.1.222:1337/

===[ Conclusion ]~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Nous avons appris une technique très sophistiquée et élaborée qui nous permet de
cacher des références à n'importe quel espace de noms en utilisant inotify. One notable advantage of this
approach is its integration within the main principale du système,
éliminant le besoin de modules noyau potentiellement restreints, surtout
dans les situations où le noyau est signé.

Cependant, nous avons à peine effleuré les possibilités et applications de
cette méthode. Une application simple et utile est un tunnel netfilter, mais le
potentiel s'étend beaucoup plus loin. For instance, there are other network
interfaces such as ipvlan or macvtap that can be valuable in certain scenarios.
Proxy ARP is another interesting concept to explore. Additionally, while we
mainly focused on network espace de nomss, user espace de nomss can also bring some joy,
as they have very interesting relationships with other espace de nomss.
