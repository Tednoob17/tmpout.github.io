.---\ Comment écrire une machine virtuelle en assembly /---.

Au début, je pense que je devrais expliquer ce qu'est une VM, pour ne pas créer de 
confusion. Lorsque l'on parle d'obfuscation binaire et de reverse engineering, une VM 
est un type de protection binaire, où le code exécuté est écrit avec un jeu 
d'instructions personnalisé (ou non) et exécuté avec un CPU émulé.

Lorsque l'on regarde un code virtualisé désassemblé, on peut voir au premier coup 
d'œil ce que la VM est capable de faire, mais pas l'ordre dans lequel les opcodes 
virtuels sont réellement exécutés.

Voyons comment j'ai créé ma propre VM avec son jeu d'instructions.
Avant d'écrire une seule ligne de code, j'ai dessiné un schéma de comment ma Machine 
Virtuelle allait fonctionner :

           +---------- SPIDER ----------+
           | main code                  |            +-- H --+ <== HandlersTable
           |                            |            |___H1__|
           | f: I -> H                  |--- EXEC ---|___H2__|
      -----|    Ii -> Hi                |            |__...__|
      |    | SPIDER = f(VX)             |            |___Hn__|
      |    +----------------------------+
      |                                |         +-- VX --+
+----------------------------------+   |--CHECK--|___I1___|
| I = Liste des instructions virtuelles |             |___I2___|
+----------------------------------+             |__...___|
                                                 |___In___|

                     -------------------------------

+--- Pile Virtuelle ---+      +---Table des Registres Virtuels ---+
|_________S1__________|      |  R1  |  R2  |  ...  |  Rn  |
|_________..._________|      +----------------------------+
|_________Sn__________|         ^--- R1 = VPC (compteur de programme virtuel)

Le virus lui-même est écrit avec le jeu d'instructions personnalisé que j'ai défini.
Pour la simplicité, j'ai choisi de donner la même taille (8 octets) à toutes
les instructions.

Prenons un exemple.
--------------------------------------------------------------------------------
%define MOV_Rx_Ry(x,y) db 0x04,x,y,0x2e,0xc3,0xec,0x92,0xf
--------------------------------------------------------------------------------
C'est l'ensemble d'opcodes correspondant à l'instruction MOV_Rx_Ry(x,y),
qui est mon équivalent virtuel d'un "mov rX, rY", comme "mov rax, rbx" en x64.

Le premier octet, 0x04 ici, représente le nombre attribué à l'instruction,
c'est ce que le spider va vérifier afin de sauter au bon handler.

x et y sont des arguments, ils sont remplacés par le numéro correspondant aux 
registres virtuels lorsque l'instruction est appelée. Par exemple MOV_Rx_Ry(1, 2) 
va déplacer la valeur stockée dans le deuxième registre virtuel dans le premier 
registre virtuel.

Voici un schéma montrant comment j'ai organisé les registres virtuels.
(chaque registre est fait de 8 octets (qword))

[VSP][r0][...][r(NBR_REG-1)][a0][a1][a2][a3][a4][a5][ret] --+
+----------------------------------------------+            |
| Contexte Virtuel : 8+8*(NBR_REG)+8*6+8 octets  | <----------+
+----------------------------------------------+
|          Pile Virtuelle : 0x600 octets        |
+----------------------------------------------+
|         Pile Réelle : beaucoup d'octets       |
+----------------------------------------------+

Les cinq derniers octets (0x2e,0xc3,0xec,0x92,0xf) sont totalement inutiles, ils ne 
sont pas utilisés par le handler, c'est pourquoi j'ai choisi des octets aléatoires, 
pour confondre les reverse engineers un peu plus.

Maintenant, admettons que nous avons un MOV_Rx_Ry(A1_PARAM, VSP) quelque part dans 
le code du virus. Cette instruction est conçue pour mettre le contenu de VSP 
(équivalent de RSP pour la pile virtuelle) dans A1, un registre d'argument de 
syscall.
Comment la VM est-elle capable de comprendre cette instruction personnalisée et de 
l'exécuter ?

La réponse est spider. C'est le nom du bout de code que j'ai écrit faisant les liens 
entre les instructions virtuelles et leurs handlers (les blocs de code réel exécutant 
ce que les instructions virtuelles sont conçues pour faire).

Le code n'est heureusement pas aussi effrayant qu'une vraie araignée, il ressemble 
à un gros bug avec 0x20 pattes mais c'est en fait un tigre en papier[1] :

----------------------------------- cut-here -----------------------------------
; not the spider, but I think it's important to keep those registers in mind:
xor rax, rax ; rax will hold the program counter (pc)
xor rbx, rbx ; rbx will be a buffer register
xor rcx, rcx ; rcx will hold the first argument of an instruction
xor rdx, rdx ; rdx will hold the second argument of an instruction
xor rsi, rsi ; rsi will point to the virtual context (list of all virutal regs)
xor rdi, rdi ; rdi will point to the virus code

; now, the spider:
spider:
  mov rbx, qword [rdi+rax] ; rbx contains the current virtual opcode

  cmp bl, 0x1 ; NOP1
  je handlers_table.NOP
  cmp bl, 0x2 ; PUSHR
  je handlers_table.PUSH_Reg
  cmp bl, 0x3 ; POP_R
  je handlers_table.POP_Reg
  cmp bl, 0x4 ; MOV_Reg_to_Reg
  je handlers_table.MOV_Reg_to_Reg
  ...
  cmp bl, 0x20
  je handlers_table.JMPNEG

  .cmp_end:
    cmp rax, virus_end-code-5
    jl spider

--------------------------------------------------------------------------------

Trivial, comme vous pouvez le voir.
Maintenant, la dernière pièce du puzzle : le handler.
Le rôle d'un handler est fondamentalement d'opérer sur les registres virtuels ou la 
pile virtuelle avec de vraies instructions, afin de faire ce que l'instruction 
virtuelle est supposée faire.

Voici le handler correspondant à MOV_Rx_Ry(Rx, Ry)

----------------------------------- cut-here -----------------------------------
.MOV_Reg_to_Reg:
  ; first we clean the registers
  xor rcx, rcx
  xor rdx, rdx

  mov cl, byte [rdi+rax+1] ; rcx = Rx
  mov dl, byte [rdi+rax+2] ; rdx = Ry

  push rbx
  mov rbx, qword [rsi+rdx*8] ; move to into rbx, the value stored in Rx
  mov qword [rsi+rcx*8], rbx ; move rbx into Ry
  pop rbx

  add rax, 0x8 ; pc += 8 (easy because each instruction is made of 8 bytes)
  jmp spider.cmp_end ; return to spider
--------------------------------------------------------------------------------

Pour appeler un syscall, j'ai écrit une instruction spéciale, nommée SYSCALL(), 
prenant comme argument le numéro du syscall.
J'ai spécialement créé des registres virtuels, les registres d'arguments, pour 
contenir les arguments du syscall.

----------------------------------- cut-here -----------------------------------
.SYSCALL:
  ; clear registers
  xor rcx, rcx
  xor rdx, rdx
  xor rbx, rbx

  mov bl, byte [rdi+rax+1] ; mov the syscall number in rbx

  ; save everything
  push rax
  push rdi
  push rsi
  push rdx
  push r10
  push r8
  push r9

  mov rdi, qword [rsi+A0] ; a0 = 1st syscall argument
  mov rdx, qword [rsi+A2] ; a2 = 3rd syscall argument
  mov r10, qword [rsi+A3] ; a3 = 4th syscall argument
  mov r8, qword [rsi+A4] ; a4 = 5th syscall argument
  mov r9, qword [rsi+A5] ; a5 = 6th syscall argument
  mov rsi, qword [rsi+A1] ; a1 = 2nd syscall argument

  ; a bit of false disassembly to hide the only syscall instruction in the whole
  ; source code
  jmp .jmp_over3+2
  .jmp_over3:
      db `\x80\x87`
  mov rax, rbx ; move the syscall number into rax to perform the syscall
  mov rbx, rsp
  syscall

  ; restore everything
  mov rsp, rbx
  pop r9
  pop r8
  pop r10
  pop rdx
  pop rsi

  mov qword [rsi+RET_REG], rax ; mov the syscall return value into the return-reg
  pop rdi
  pop rax

  ; go to the next instruction
  add rax, 0x8 ; pc += 8
  jmp spider.cmp_end
--------------------------------------------------------------------------------
