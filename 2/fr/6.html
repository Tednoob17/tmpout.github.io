-= Introduction

Entrons directement dans le vif du sujet et définissons d'abord le "préchargement 
du linkeur". Cette technique fait référence à l'idée que l'on peut manipuler le 
loader ELF du noyau (voir linux/fs/binfmt_elf.c) pour passer l'exécution à un 
programme interprète personnalisé au lieu du vrai dynamic linker.

Notez que le terme 'programme interprète' fait généralement référence au dynamic 
linker, c'est-à-dire "/lib64/ld-linux.so". Aussi connu sous le nom de RTLD 
(Runtime loader). Ce papier porte sur la création d'un 'programme interprète' 
alternatif qui est chargé avant le dynamic linker lui-même.

Ne confondez pas la technique de "préchargement du linkeur" avec le "préchargement 
de bibliothèque partagée". La variable d'environnement LD_PRELOAD demande au 
dynamic linker de précharger un ensemble spécifique de bibliothèques partagées 
avant toutes les autres. La technique que nous présentons précharge le dynamic 
linker (c'est-à-dire "/lib64/ld-linux.so") et un programme interprète alternatif 
est invoqué à la place.

En méditant sur le concept d'écriture d'un programme interprète ELF personnalisé, 
nous réalisons que les possibilités sont vastes. Instrumentation de processus, 
chargement de modules, transformation de programme, etc. Notre runtime linker 
d'exemple est juste un exemple minimal de chargeur de modules, qui charge des 
objets relocalisables en mémoire et crée un environnement runtime pour que les 
modules s'exécutent avant le RTLD.

Du point de vue d'un attaquant on peut utiliser ce concept pour concevoir 
trivialement des rootkits, virus, et autres variantes APT (Advanced persistent 
threats). Du point de vue de la sécurité je vois la possibilité d'utiliser les 
concepts de ce papier pour construire des modules de sécurité pour durcir l'image 
du processus et atténuer de nombreux types d'attaques. Cependant, dans l'esprit 
d'être exotique et innovant j'ai décidé d'armer ce concept en un infecteur de 
virus modulaire qui se propage via le préchargement du linkeur.

-= Comprendre la technique

Élaborons d'abord sur le fonctionnement de cette technique de préchargement du 
linkeur. Rappelez-vous que les exécutables liés dynamiquement ont un type 
d'en-tête de programme appelé 'PT_INTERP' qui contient le chemin vers le RTLD, 
généralement "/lib64/ld-linux.so". Ce chemin peut facilement être remplacé par 
le chemin du programme interprète que nous souhaitons précharger. Nous disons 
"précharger" parce que nous chargeons notre interprète personnalisé avant 
l'interprète réel, le RTLD Linux.

NOTE : Les termes "Runtime Linker" et "Programme interprète" sont utilisés 
indifféremment dans ce papier.

Jetons un œil rapide au segment PT_INTERP de tout exécutable ELF dynamique.

$ readelf -l /bin/ls | grep -C 2 INTERP
  
  INTERP         0x0000000000000318 0x0000000000000318 0x0000000000000318
                 0x000000000000001c 0x000000000000001c  R      0x1
      [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]

Nous pouvons voir que l'offset du chemin de l'interprète est à l'offset 0x318 
dans le fichier ELF. Cette chaîne terminée par NULL peut être remplacée par 
"/lib64/evil.ld", qui est le chemin vers notre runtime linker personnalisé.

			[virus_module.o]


Comme nous pouvons le voir dans le diagramme ASCII ci-dessus. Le noyau lit le 
segment PT_INTERP pour obtenir le chemin vers le programme interprète. Le flux 
d'exécution est transféré vers /lib64/evil.ld qui est notre programme interprète 
personnalisé pour charger et linker les modules runtime. Cela crée un environnement 
runtime pour du code parasite qui est modulaire et dynamique sans déclencher les 
heuristiques de détection habituelles pour les infections ELF. Cette technique 
d'infection est en elle-même bénigne car ses intentions sont déterminées par le 
code dans le module lui-même. Dans notre preuve de concept le module est un Virus 
qui infecte d'autres binaires en remplaçant leur chemin d'interprète pour pointer 
vers "/lib64/evil.ld" ce qui à son tour fait que le binaire infecté charge 
"virus_module.o", et ainsi de suite.

-= Concevoir un interprète personnalisé pour charger des modules

Discutons de notre objectif de conception. Nous voulons écrire un interprète 
personnalisé dont le but est de charger et exécuter furtivement du code modulaire 
avant de passer le contrôle au vrai dynamic linker "/lib64/ld-linux.so" (aka RTLD).

Nos modules sont écrits en C et compilés comme des objets relocalisables. Le point 
d'entrée du module est main(). Le code C peut faire des appels à libc. Lorsque le 
code est compilé en objet de code relocalisable il a toutes les données de 
relocalisation nécessaires pour le linker dans un image ELF runtime exécutable avec 
un PLT et un GOT pour résoudre les appels dans libc. Puisque notre interprète 
s'exécute avant le dynamic linker, comment alors nous attendons à ce que notre 
module fasse des appels libc ? La bibliothèque musl-libc est liée statiquement 
dans l'interprète et nous pouvons gérer les relocalisations d'appel PLT en les 
résolvant vers les symboles libc dans l'interprète personnalisé lui-même. Cela 
peut bien sûr être amélioré, mais pour l'instant avoir accès à seulement libc est 
suffisant pour écrire des modules assez sophistiqués sans beaucoup de travail.

-= Un algorithme pour notre interprète

Notre programme interprète devrait exécuter les tâches suivantes dans l'ordre.

1. Localiser l'adresse du vecteur auxiliaire.

Nous pouvons trouver l'adresse de auxv en localisant d'abord `char **envp` sur 
la pile, puis en itérant jusqu'à sa dernière entrée + 1. Le vecteur auxiliaire 
existe en haut de la pile juste après les pointeurs de variables d'environnement.

-- Diagramme du vecteur auxiliaire sur la pile x86.

BASSE MÉMOIRE				      HAUTE MÉMOIRE
<------------------------------------------------------->
[argc][argv0 ... argvN][envp0 ... envpN][vecteur auxiliaire]


2. Analyser le vecteur auxiliaire et stocker ses valeurs pour une utilisation 
ultérieure.

Le vecteur auxiliaire contient des paires clé/valeur qui sont pertinentes pour 
la capacité du dynamic linker à se localiser lui-même et l'exécutable cible en 
mémoire. Il contient des paires clé/valeur qui sont également importantes pour 
notre interprète personnalisé.

3. Mapper les segments du dynamic linker "/lib64/ld-linux.so" en mémoire.

Nous devons mapper chaque segment PT_LOAD du dynamic linker "/lib64/ld-linux.so" 
en mémoire à l'adresse virtuelle alignée sur page correcte. L'adresse du point 
d'entrée prise de l'en-tête ELF est une valeur d'offset qui doit être calculée 
avec l'adresse de base du segment text et stockée pour une utilisation ultérieure 
à l'étape 10.

4. Définir l'entrée AT_BASE du vecteur auxiliaire à l'adresse du segment text 
de "/lib64/ld-linux.so" maintenant mappé en mémoire.

Les valeurs du vecteur auxiliaire sont juste des valeurs de pile et peuvent donc 
être réécrites. Lorsque le noyau mappe le programme interprète en mémoire il 
définit l'entrée auxiliaire AT_BASE à l'adresse de base de l'interprète ELF mappé.

Lorsque nous transférons le flux d'exécution d'un interprète (c'est-à-dire 
"/lib64/evil.ld") vers un autre (c'est-à-dire "/lib64/ld-linux.so"), 
l'interprète source doit réinitialiser AT_BASE de sa propre adresse de base vers 
l'adresse de base de l'interprète de destination. Les interprètes doivent connaître 
leur propre adresse de base s'ils sont PIE afin qu'ils puissent effectuer des 
relocalisations relatives sur leur propre code et données au runtime. Le dynamic 
linker est une bibliothèque partagée et nécessite beaucoup de relocalisations qui 
calculent sa propre adresse de base.

5. Analyser le fichier objet relocalisable module 'virus_payload.o'.

La table de relocalisation doit être analysée. Toute relocalisation de type 
R_X86_64_PLT32 doit être notée afin qu'assez de place puisse être créée dans le 
segment text pour les stubs PLT. Dans notre implémentation de "/lib64/evil.ld" 
nous utilisons un linking strict, et avons donc des stubs PLT très simples :

lp_loader.c:18
```
 // jmp *0x0(%rip)
 uint8_t plt_stub[6] = "\xff\x25\x00\x00\x00\x00";
```

Le stub PLT fait simplement un jump indirect vers le GOT[entry] respectif. Notre 
implémentation de linker est quelque peu naïve car nous créons une entrée PLT pour 
chaque relocalisation PLT. Parfois il y a plusieurs relocalisations PLT pour le 
même symbole, et notre linker naïf crée des PLT/GOT dupliqués. Cela peut être 
facilement corrigé dans une version future pour qu'un symbole donné corresponde 
toujours à une seule entrée PLT.

6. Créer un environnement runtime exécutable adapté pour que le module s'exécute.
Un segment text, segment data et .bss doivent être créés avec des mappings mémoire 
anonymes en utilisant mmap(2).

Notre objectif est de créer une image runtime exécutable à partir d'un objet 
relocalisable. Il n'y a pas de segments PT_LOAD dans un objet relocalisable donc 
nous devons déterminer la taille du segment text et data en regardant les en-têtes 
de section correspondants.

Toutes les sections de type SHF_ALLOC et SHF_ALLOC|SHF_EXEC doivent être mappées 
dans le segment text.

Toutes les sections de type SHF_ALLOC|SHF_WRITE doivent être mappées dans le 
segment data.

La taille .bss est stockée dans le membre sh_size de son en-tête de section. 
Assurez-vous d'étendre le mapping du segment data de shdr[.bss].sh_size octets.

Nous n'avons pas besoin de créer un segment heap, car tout appel à malloc() sera 
exécuté via musl-libc qui est lié statiquement à notre interprète. Par conséquent 
le module partagera un segment heap avec l'interprète.

7. Résoudre toutes les relocalisations pour l'objet module.

Le module peut faire des appels à libc qui seront rendus possibles en créant des 
entrées PLT et GOT pour les relocalisations R_X86_64_PLT32 trouvées dans l'objet 
relocalisable. Les appels externes à libc seront résolus vers les symboles musl-libc 
qui seront liés statiquement dans notre interprète.

Notre module exemple 'virus_payload.o' contient seulement les types de 
relocalisation R_X86_64_PLT32 et R_X86_64_PC32, ce que tout notre linker gère 
actuellement. Voir `bool relocate_module(struct evil_linker *linker)` dans lp_loader.c.

Jetons un œil rapide à comment résoudre les relocalisations qui sont dans notre 
objet module.

Relocation section '.rela.text' at offset 0x970 contains 34 entries:
  Offset          Info           Type           Sym. Value    Sym. Name + Addend
000000000033  000c00000004 R_X86_64_PLT32    0000000000000000 open - 4
000000000043  000500000002 R_X86_64_PC32     0000000000000000 .rodata - 4
... truncated ...


Résoudre le type de relocalisation R_X86_64_PLT32 nécessite que nous ayons 
d'abord créé un PLT dans l'image exécutable du module. Notre implémentation de 
linker place le PLT à la toute fin du segment text. Les instructions d'appel qui 
se résolvent vers des symboles externes ont une relocalisation PLT32 qui doit être 
résolue. En fait le compilateur peut aussi émettre des relocalisations PLT32 pour 
des appels à tous les types de symboles GLOBAL, même s'ils sont définis localement 
dans le module.

La relocalisation R_X86_64_PLT32 est pour calculer et patcher l'offset d'appel 
vers une entrée PLT donnée. Selon la spécification ELF le calcul suivant résout 
la relocalisation : L + A - P

Cela peut être décomposé en : 
[open@plt] + rel->r_addend - (text_segment_addr + rel->r_offset)


La relocalisation R_X86_64_PC32 est utilisée pour patcher les offsets vers 
diverses instructions qui référencent la mémoire, et nécessite le calcul suivant :
S + A - P

Cela peut être décomposé en :
[symval of .rodata] + rel->r_addend - (text_segment_addr + rel->r_offset)

Notre implémentation de ceci peut être trouvée dans lp_loader.c:apply_relocation()

Une fois que le module a été transformé en image runtime exécutable dont les 
relocalisations ont été entièrement satisfaites nous pouvons transférer le 
contrôle de notre interprète au module chargé.

8. Transférer le contrôle à la fonction main() du module avec une instruction call.

Nous transférons le contrôle à notre module Virus avec une instruction call, afin 
que le flux d'exécution retourne. Le point d'entrée du module est l'adresse du 
symbole "main". Une fois que le module Virus a fini de s'exécuter, le contrôle 
est passé de retour à notre interprète.

```
static inline void
transfer_to_module(uint64_t entry)
{
        __asm__ __volatile__ ("mov %0, %%rax\n"
                              "call %%rax" :: "r" (entry));
        return;
}
```

9. Transférer le contrôle au Dynamic Linker "/lib64/ld-linux.so"

Le dynamic linker est mappé en mémoire à présent, et nous devrions avoir sa 
valeur de point d'entrée stockée depuis l'étape 4. Voici les étapes pour 
transférer le contrôle au dynamic linker :

	1. Effacer toutes les valeurs de registre
 
	2. Définir la valeur de RSP à la valeur de &argc, car le rtld s'y attend.
	
	-- Diagramme du vecteur auxiliaire sur la pile x86.

	3. Définir la valeur de RAX à l'adresse du point d'entrée de l'exécutable cible.

	4. Transférer le contrôle au dynamic linker. Notre implémentation utilise un 
	push/ret pour sauter vers le rtld.

	```
                                            "ret" :: "r" (stack), "g" (addr), "g"(entry))
	```

Une fois le contrôle passé au RTLD notre travail est fait. Le RTLD gèrera 
toutes les relocalisations pour charger les objets partagés et patcher 
l'exécutable cible. Le RTLD transfèrera ensuite le contrôle au point d'entrée 
de l'exécutable.

-= Compiler et linker notre interprète

Nous construisons l'interprète lui-même comme un exécutable lié statiquement 
avec une adresse de base text de 0xa0000000 comme spécifié par un script de 
linker personnalisé. L'interprète est un ELF exécutable standard ET_EXEC, et 
est lié statiquement avec musl-libc et une version légèrement modifiée de 
libelfmaster. Pour nos besoins immédiats de test et recherche c'était idéal, 
cependant l'interprète peut aussi être construit comme un exécutable PIE ou 
une bibliothèque partagée comme le RTLD.

- Une note sur la résolution de symboles :

Lorsque notre code virus_payload.c tente d'appeler des fonctions musl-libc qui 
ne sont pas dans la table des symboles de notre interprète ELF, elles ne seront 
pas résolues. Toutes les fonctions musl-libc qui ne sont pas utilisées par 
l'interprète ne seront pas incluses dans sa table des symboles, sur laquelle 
nous comptons pour la résolution des symboles du module. Une solution de contournement 
est simplement d'inclure tous les symboles libc invoqués par votre code de module 
dans le Makefile pour l'interprète en utilisant le flag ld '-undefined=<symbol>'. 
Une autre option est d'utiliser le flag de linker '--whole-archive' pour que tous 
les symboles possibles de libc soient inclus dans le binaire de l'interprète.
