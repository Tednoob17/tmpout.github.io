Les analyseurs de fichiers sont un composant central de tout système informatique

[ 1.0 Hypothèses d'endianness ]────────────────────────────────────────────────────────//──

Ce bug affecte beaucoup de bibliothèques d'analyse. Je l'ai remarqué à l'origine 
il y a quelques années lorsque j'ai commencé à mettre du code dans ei_data à 
l'intérieur de l'en-tête ELF et à réaliser à quel point cela perturbait divers outils.

Ceci est un exemple d'un binaire Mirai décompressé, non strippé, ciblant MIPS.

Dans un fichier ELF, l'endianness est définie par le champ ei_data de l'en-tête ELF. 
Dans un binaire MIPS big endian, ei_data = 2. Pour tous les binaires little endian, 
ei_data = 1. 

┌─ ELF HEADER - 16 premiers octets ────────────────────────────────────────────────────────┐
│ A ei_magic    "\x7fELF"                                                              │
│ B ei_class    1 = 32 Bit, 2 = 64 Bit (A-ackshully: If LSB = 1, 32 bit, else, 64 bit) │
│ C ei_data     1 = Little Endian, 2 = Big Endian                                      │
│ D ei_version  ELF Version, only "1" is defined                                       │
│ E ei_osabi    OS/ABI Version                                                         │
│ F ei_pad      8 Bytes, 4 U :3                                                        │
└──────────────────────────────────────────────────────────────────────────────────────┘

La première partie de l'en-tête de notre binaire ressemble à ceci :

  ELFHEADER A───────┐ B┐C┐ D┐E┐ F─────────────────┐
  00000000: 7f45 4c46 0102 0100 0000 0000 0000 0000  .ELF............

Ce champ est important, parce que les structures dans l'en-tête ELF sont stockées 
en fonction de l'endianness de la machine cible.

Cela arrive aussi si ei_data est 0. C'est dû à l'hypothèse d'endianness que beaucoup 
d'outils font par défaut. Supposer que les données sont en little endian à moins que 
ce ne soit explicitement spécifié peut conduire à des problèmes de mauvaise analyse 
qui vont se propager à travers une pile d'analyse complexe. Nous verrons pourquoi 
ceci est important plus tard dans ce papier.

Le champ e_machine est traité comme 0x800. C'est parce que le numéro e_machine pour 
MIPS est 8, mais l'ordre des octets est incorrect. Dans le source de binutils, il 
est également indiqué que ce champ est officiellement pour "big-endian only".

https://github.com/bminor/binutils-gdb/blob/master/include/elf/common.h#L115

  #define EM_MIPS     8 /* MIPS R3000 (officially, big-endian only) */

:: 1.2 Casser Virus Total et contourner l'analyse heuristique ::::::::::::::::::::::::::::::

Un scan Virus Total sur le binaire non modifié a 32 détections pour Mirai. Le même 
ELF avec ei_data défini à 1 a seulement 8 détections. En changeant juste 1 bit dans 
l'en-tête ELF, nous pouvons réduire les détections de 75%. Ceci n'a rien qui inhiberait 
l'analyse heuristique pour les signatures Mirai connues, donc une réduction des 
détections est assez significative étant donné à quel point ces binaires sont bien 
documentés.

Cette même chose arrive avec les ELF x86-64. C'est arguanblement plus noticeable 
pour un analyste de voir quelque chose marqué comme big endian quand la plupart des 
binaires qu'il rencontre sont little endian, mais c'est toujours quelque chose dont 
il faut être conscient. Beaucoup d'analyse de malware est faite par des outils 
avancés qui reposent sur des analyseurs contenant ces bugs sous le capot.

Compilons un programme simple pour démontrer.

Les analyseurs devraient vérifier e_machine sans essayer de deviner l'endianness 
d'abord, puis comparer à une liste de valeurs machine connues, présentées dans l'ordre

:: 2.1 Noyau Linux - SIGBUS via p_offset ::::::::::::::::::::::::::::::::::::::::::::::::::

Ce bug est déclenché simplement en rendant p_offset dans un en-tête de programme 
plus grand que le fichier lui-même. Cela arrive parce que l'analyseur ELF dans le 
noyau Linux suppose que l'en-tête de programme dit la vérité quand il demande où 
charger et stocker une certaine section du binaire en mémoire.

[ POC ]

  $ base64 -d <<< f0VMRgIBAQAAAAAAAAAAAAIAPgABAAAAeABAAAAAAABAAAAAAAAAAAAAAAAAAAAAAAAAA\
    EAAOAABAAAAAAAAAAEAAAAFAAAAABAAAAAAAAAAAEAAAAAAAAAAQAAAAAAAABAAAAAAAAAAEAAAAAAAAAIA\
    AAAAAAAAkJCwPGa/BgAPBQ== > ns.sigbus.elf
  $ chmod +x ns.sigbus.elf
  $ ./sigbus.elf

[ Comment cela arrive-t-il ? ]

Lorsque Rizin configure un binaire pour l'analyse, il crée un objet avec des 
informations sur le binaire. Cette structure est peuplée pendant l'analyse du 
fichier, avec les sections et leurs données associées groupées dans un grand vecteur.

L'analyseur itère sur l'en-tête ELF pour trouver où sont les en-têtes de Programme 
et de Section, puis itère sur ceux-ci pour traiter d'autres parties du fichier. 
Parce qu'un fichier ne mentirait jamais, la plupart des analyseurs prendront ces 
offsets stockés dans les en-têtes et les traiteront comme les données qu'ils 
s'attendent à trouver. Il y a souvent des vérifications pour savoir si les valeurs 
existent, mais pas nécessairement si elles sont dans une plage raisonnable.

Voici le déroulement de base de ce qui déclenche ce bug :

  1.0 : rz_bin_elf_init prend l'ELFOBJ qui représente le fichier lui-même en mémoire.
  1.1 : Vérifie s'il a les en-têtes qu'il s'attend à trouver.
  1.2 : Crée un vecteur pour contenir toutes les sections du binaire
  2.0 : Appel à rz_bin_elf_init_shdr pour initialiser le vecteur d'en-têtes de section.
  3.0 : Appel à rz_bin_elf_convert_sections, qui crée un autre vecteur en itérant
       sur les en-têtes de section.
  4.0 : Ça réussit, et suit avec une vérification pour d'autres segments via 
       rz_bin_elf_has_segments, qui appelle ensuite get_sections_from_dt_dynamic.
  5.0 : get_sections_from_dt_dynamic appelle quelques fonctions pour vérifier ce qui 
       peut être fait avec la section donnée.
  5.1 : Après que toutes ces vérifications échouent, crée un autre rz_vector, et tente 
       un dernier appel à la dernière vérification possible : create_section_plt.
  6.0 : Cela invoque create_section_from_phdr, qui pousse un nouvel élément sur le 
       vecteur existant, et commence à ajouter des informations à celui-ci.
  6.1 : Cela échoue, à cause de la vérification sur section->offset, qui est déjà 
       hors des limites du fichier. section->offset est défini avant que cette 
       vérification ne se produise.
  7.0 : Tout cela cause la vérification en 5.1 à échouer, ce qui résulte en un appel 
       à rz_vector_free.
  8.0 : Cela itère sur les éléments du vecteur (y compris le faux section->offset), 
       et les libère pour la longueur du vecteur.
  9.0 : Le pointeur section->offset est notre valeur de pointeur arbitraire.

Les calculs de pointeur sont perturbés en raison de quelques facteurs ici.

Dans des circonstances normales, l'offset d'en-tête de section pointe vers une table 
d'en-têtes de section, et l'analyseur itère sur eux pour comprendre quelles sections 
existent dans le binaire.

L'offset d'en-tête de section du binaire original était 0x71B8, avec 0x1C en-têtes 
de section qui sont de 0x40 de longueur.

  0x1C x 0x40 = 0x700

Cela a du sens parce que le fichier se termine à 0x78B8, ce qui signifie que le 
fichier original a les sections qui vont de 0x71B8 à la fin du fichier.

Notre fichier malveillant se termine à 0x994C, mais a un offset d'en-tête de section 
de 0x91D8, avec 0x1E en-têtes de section.

  0x1E x 0x40 = 0x780

  Adresse de fin d'en-tête de programme : 0x91D8 + 0x780 = 0x9958

Le pointeur vers le tampon d'en-tête de section est maintenant après la fin du 
fichier en mémoire. Cela conduit à des lectures et écritures hors bornes, et un 
pointeur corrompu dans l'analyseur.

Il y a deux points à retenir ici :

1. Assurez-vous de vérifier que le nombre total d'éléments itérables et leurs tailles 
   correspondent à la vraie taille du tampon.
2. N'allouez pas de vecteurs en mémoire sans vérifier qu'ils seront réellement remplis.

Voir ce lien pour ce à quoi ressemblait la fonction vulnérable avant le correctif :
https://github.com/rizinorg/rizin/blob/0e11486f36aa784b471d8d4ecf291a8d962b4c47
  /librz/bin/format/elf/elf_sections.c#L66

Ceci est le POC TikTok : https://vm.tiktok.com/ZM8S7SFK1/

[ 3.0 Mauvaise analyse des nombres magiques ]─────────────────────────────────────────//──

Ce n'est pas un bug d'analyseur ELF à proprement parler, mais un problème général 
avec l'analyse de fichiers dans son ensemble. Nos outils d'analyse binaire et 
débogueurs supportent généralement plus d'un type de fichier binaire. Même au sein 
des familles de types de fichiers, les analyser correctement peut être délicat (comme 
vu ci-dessus), donc obtenir le type correct est crucial.

:: 3.1 radare2 5.3.1 : CVE-2021-3673 A.K.A. Le bug "LELF" ::::::::::::::::::::::::::::::::::

Ce bug a également été trouvé via fuzzing. Je travaillais sur le fuzzing de l'en-tête 
ELF, vérifiant des choses qui pourraient dérouter un outil d'analyse de fichiers 
(comme le bug d'endianness) tout en étant toujours capable de s'exécuter correctement.

Après avoir fait l'analyse de crash, il est apparu que ce bug particulier pouvait 
être déclenché simplement en changeant le premier octet de n'importe quel binaire 
ELF en un "L". Dans radare2, cela invoque l'analyseur Linear Executable.

Les Linear Executables sont une variété précoce de fichiers EXE, principalement 
utilisés pour les drivers VxD pour Windows (2.0 - 9x). C'est lié à PE, avec un 
stub DOS et un pointeur vers l'en-tête LE. Parce que la signature LE est connue, 
elle est incluse dans la façon dont radare2 scanne les types de fichiers dans 
l'en-tête lorsqu'il essaie de déterminer le type de fichier. Malheureusement, 
l'analyseur binaire configure un objet binaire pour l'en-tête LE, sans qu'il soit 
vraiment au bon endroit.

Il analyse l'exécutable prématurément avec quelles que soient les valeurs qui 
étaient déjà initialisées, et commence à itérer sur l'en-tête en pensant que le 
reste du code de configuration a été pris en charge. Dans la fonction __get_entries, 
il lance ce processus, finissant par rencontrer un pointeur vers un endroit qui 
n'a rien d'alloué, et finit par boucler sur ce qu'il pense être des en-têtes, mais 
le compteur d'en-têtes est également corrompu. Cela consomme lentement toute la 
mémoire système résultant en un DOS.

:: 4.2 Lectures (et écritures ?) hors bornes - Abus des sections dynamiques ::::::::::::::::::

Les entrées dans la section dynamique d'un ELF contiennent généralement beaucoup 
d'adresses relatives au début d'une section dans le binaire. Par ce biais, il y a 
quelques changements simples que vous pouvez apporter à un binaire qui feront que 
ld fera des choses incorrectement, jusqu'à et y compris s'analyser lui-même en mémoire.

Pour démontrer, regardons la section .gnu.version_r. Vous pouvez lire cette section 
si elle existe en utilisant :

  $ readelf -V yourbinary

À propos de cette section de la référence LSB :

  Les définitions de symboles sont contenues dans la section spéciale .gnu.version_r 
  qui a un type de section de SHT_GNU_verneed. Le nombre d'entrées dans cette section 
  est contenu dans l'entrée DT_VERNEEDNUM de la Section Dynamique. Le membre sh_link 
  de l'en-tête de section pointe vers la section qui contient les chaînes référencées 
  par cette section.

  RÉF : https://refspecs.linuxfoundation.org/LSB_1.3.0/gLSB/gLSB/symverrqmts.html

Il y a deux façons dont vous pouvez utiliser ces sections pour déclencher des bugs, 
soit via la structure Elfxx_Verneed principale, ou une des entrées Elfxx_Vernaux.

Voici quelques exemples du binaire que je testais :

  ┌ Elfxx_Verneed ───────────────────────────────────────────────────────────────────┐
  │ DATA        NAME         DESCRIPTION                                             │
  │ 0100 ────── vn_version ─ Version de la structure. ld ne traite que la version 1.  │
  │ 0500 ────── vn_cnt ───── Nombre d'entrées de tableau vernaux associées.             │
  │ 0100 0000 ─ vn_file ──── Offset de la chaîne de nom de fichier dans l'en-tête de  │
  │                          section.                                                 │
  │ 1000 0000 ─ vn_aux ───── Offset de l'entrée correspondante dans le tableau vernaux. │
  │ 0000 0000 ─ vn_next ──── Offset de la prochaine entrée verneed.                    │
  └──────────────────────────────────────────────────────────────────────────────────┘
  ┌ Elfxx_Vernaux ───────────────────────────────────────────────────────────────────┐
  │ DATA        NAME         DESCRIPTION                                             │
  │ 1369 690d ─ vna_hash ─── Valeur de hash du nom de dépendance (fonction ELF hash). │
  │ 0000 ────── vna_flags ── Masque de bits d'information de dépendance.               │
  │ 0600 ────── vna_other ── Identifiant de version de fichier objet utilisé dans le   │
  │                          tableau de versions de symboles .gnu.version. Si le bit 15 │
  │                          est défini, cet objet est ignoré par le linker.           │
  │ 7302 0000 ─ vna_name ─── Offset de la chaîne de nom de dépendance dans l'en-tête   │
  │                          de section.                                               │
  │ 1000 0000 ─ vna_next ─── Offset de la prochaine entrée vernaux.                    │
  └──────────────────────────────────────────────────────────────────────────────────┘

Verneed.vn_file est l'offset de la table de chaînes pointant vers le nom du fichier 
nécessité par le binaire. C'est non signé, donc vous pouvez le définir jusqu'à 
n'importe quelle adresse dans les 32 bits inférieurs de l'adresse virtuelle. ld 
fera alors un strcmp pour le vérifier contre d'autres valeurs connues. Pendant le 
strcmp, RDI et RBP pointent tous les deux vers l'emplacement mémoire. Vous pouvez 
déclencher une condition de DOS en pointant cela vers une adresse qui n'existe pas.

Les structures Vernaux sont analysées de manière similaire. Vernaux.vna_name peut 
pointer vers une adresse qui est chargée dans l'image du processus. Il est sujet 
à des vérifications similaires et peut déclencher des conditions DOS dans strcmp 
ou d'autres fonctions appelées par _dl_check_map_versions. Si le nom ne peut pas 
être résolu, alors ld le rapportera et le programme se terminera.

Pour jouer avec ceci, j'ai ajouté de l'art ASCII à la fin de mon binaire puis ai 
redimensionné la dernière section PT_LOAD pour m'assurer que le reste du binaire 
se retrouvait dans l'image du processus. Ensuite j'ai pointé une structure Vernaux 
vers le début du tampon, et l'ai fait échouer la vérification et imprimer mon art. 
Cool !

Vous pouvez aussi prendre la plupart des offsets dans la section dynamique, comme
