*** eBPF, BPF, Linux Kernel, guide, tips

+-#- Introduction -#-
|
| Il y a environ six mois j'ai commencé un nouveau travail et me suis plongé dans 
| l'ajout de Berkeley Packet Filters (BPF) comme source de télémétrie pour notre 
| agent de sécurité endpoint Linux. Ce travail a culminé avec la release de trois 
| bibliothèques open source ([0], [1], [2]). Ce n'est pas de ça dont il s'agit, 
| cependant. Ceci est sur les problèmes que nous avons rencontrés en implémentant 
| BPF en tant que défenseurs, et comment les défenseurs peuvent utiliser BPF dans 
| leurs environnements (bien que les attaquants devraient également trouver des 
| conseils utiles ici). Je suis passé par toutes les PR, tickets Jira et messages 
| des six derniers mois pour mettre ensemble cette liste de pièges BPF et leurs 
| solutions. J'espère que cela aide les défenseurs, développeurs et chercheurs à 
| se mettre à niveau avec BPF plus vite que je ne l'ai fait.
| 
| Note : Je vais utiliser BPF pour signifier eBPF étendu (eBPF), puisque c'est le 
| nom officiel. Pas à confondre avec l'ancien BPF classique (cBPF). Je vais aussi 
| supposer que vous êtes *lâchement* familier avec BPF, suffisamment pour 
| considérer de le déployer ou non dans votre environnement.
+-

+-#- Pourquoi même utiliser BPF ? -#-
| 
| Vous vous demandez peut-être, "si vous remplissez un article d'avertissements à 
| propos de BPF, pourquoi devrais-je même m'embêter à essayer de l'utiliser ?" 
| Excellente question, homme de paille. Il y a un certain nombre de choses que BPF 
| fait vraiment, vraiment bien et que vous devriez considérer.
| 
| - **Vous pouvez obtenir de la visibilité (presque) où vous voulez.** S'il y a un 
| chemin de code spécifique dans le noyau (ou userspace) que vous savez sera exécuté 
| pendant une attaque, vous pouvez vous mettre là. S'il y a une valeur de payload 
| dans un paquet que vous devez voir avant qu'il n'atteigne vos règles `iptables`, 
| vous pouvez faire ça. Vous voulez modifier ou bloquer les arguments de syscall ? 
| Vous pouvez faire ça aussi.
|
| - **Vous pouvez ré-instrumenter dynamiquement.** Vous changez d'avis sur ce que 
| vous voulez inspecter ? Changez-le pendant que c'est en cours d'exécution. Vous 
| pouvez soit échanger l'ensemble du programme (bien que cela pourrait ne pas être 
| possible dans le futur avec les programmes BPF signés[4]) soit modifier le 
| comportement en mettant à jour les maps BPF depuis l'espace utilisateur.
|
| - **C'est sûr !** Vous pouvez faire toutes ces choses avec un Module Noyau Linux 
| (LKM), bien sûr, mais la Machine Virtuelle BPF (BPF-VM) et le vérifieur assurent 
| (ou du moins essaient vraiment fort d'assurer[17]) que vous ne pouvez pas paniquer 
| ou casser le noyau.
|
| - **C'est conscient des conteneurs, ou du moins ça peut l'être.** Les alternatives 
| d'instrumentation comme `auditd` ont tendance à avoir des difficultés dans les 
| environnements conteneurisés, retournant des valeurs qui n'ont de sens que dans 
| certains namespaces, ou perdant complètement la trace des choses. BPF, en revanche, 
| peut vous donner des informations dans le contexte que vous voulez (tant que vous 
| le programmez de cette façon).
|
| - **C'est rapide.** Faites autant de travail que possible dans le programme BPF 
| avant d'envoyer des informations vers l'espace utilisateur, et vous pouvez éviter 
| des changements de contexte coûteux ou un enrichissement de données sujet aux 
| race conditions.
|
| - **C'est atomique (en quelque sorte).** Les programmes BPF ne sont généralement 
| pas préemptables (il y a des exceptions[5]). Cela s'applique également aux tail 
| calls, donc vous pouvez configurer une logique assez complexe dans votre 
| instrumentation sans trop vous soucier de la réentrance.
+-

+-#- Le problème avec BPF. -#-
| 
| Du point de vue de ce rédacteur, il y a deux problèmes principaux avec BPF : 1) 
| il est maintenant utilisé de manières pour lesquelles il n'a jamais été conçu 
| (c'est-à-dire qu'il évolue naturellement au fil du temps) et 2) il y a un large 
| chevauchement dans les mainteneurs du sous-système BPF du noyau Linux et des 
| outils BPF userspace. 
| 
| Voici des problèmes concrets découlant de (1) :
| 
| - BPF n'est pas vraiment CO-RE (Compile Once - Run Everywhere), c'est plus CE-RO 
| (Compile Everywhere - Run Once). Beaucoup d'outils userspace "atteignent" le CO-RE 
| en pratique en compilant sur la machine hôte. Les nouvelles vraies fonctionnalités 
| CO-RE sont... nouvelles. Il y a des chances que vous deviez supporter un noyau 
| qui ne les a pas. La fin de vie ne veut pas dire grand-chose quand l'hôte exécute 
| une fonction critique pour l'entreprise et que les costumes voient trop de risque 
| à le mettre à jour. Et charger une toolchain complète pour compiler des programmes 
| BPF sur l'hôte est souvent également impossible.
| 
| - Les toolchains et bibliothèques sont conçues autour des cas d'utilisation de 
| type `bpftrace`. C'est-à-dire, des outils one-shot pour diagnostiquer des problèmes 
| spécifiques. Le livre de Brendan Gregg[7] est une excellente ressource pour ça. 
| Maintenant que BPF pour les daemons de longue durée gagne en popularité, les 
| mainteneurs travaillent dur à ajouter des fonctionnalités pour supporter ça 
| (comme le véritable CO-RE mentionné ci-dessus). Malheureusement, encore une fois, 
| ces fonctionnalités n'existeront probablement pas sur les noyaux que vous devez 
| supporter.
| 
| - Il y a beaucoup de types différents de programmes BPF (que nous allons couvrir), 
| qui ont tous des sémantiques de chargement et d'exécution variables. Selon que 
| vous voulez exécuter un kprobe ou un classificateur TC, vous devrez utiliser des 
| méthodes entièrement différentes pour le faire. Et pendant que vous les écrivez, 
| les helpers disponibles pour vous peuvent varier énormément. Et la documentation 
| est incomplète, dispersée, et souvent obsolète, parce que...
| 
| Et voici quelques exemples spécifiques de problèmes découlant de (2) :
| 
| - À cause du chevauchement, la documentation des interfaces BPF pures (il y a une 
| pléthore, nous allons couvrir ça) fait défaut. Les gens qui la maintiennent 
| écrivent les outils userspace, donc ils n'ont pas besoin de documentation 
| approfondie. Sérieusement, allez consulter la manpage BPF pour la distro sur 
| laquelle vous êtes. Il y a des chances qu'elle manque beaucoup de helpers et 
| qu'il y ait plus d'un "TODO : remplissez ceci" qui est là depuis des années. 
| Pourquoi ne pas utiliser leurs outils userspace ? Eh bien...
| 
| - Leurs outils userspace sont un labyrinthe magique. Pour s'approcher du CO-RE 
| d'une manière rétrocompatible, ils sont remplis de bricolages que vous n'avez 
| probablement pas besoin. Idéalement, vous vous interfaceriez directement avec les 
| syscalls sous-jacents et n'utiliseriez que ce dont vous avez besoin. Mais faire 
| ça n'est pas documenté. Et, à cause des problèmes de documentation, il n'y a 
| vraiment pas d'élan communautaire pour simplifier ces bibliothèques. Parce que 
| ces bibliothèques couvrent (jusqu'à récemment, voir (1)) la majorité des cas 
| d'usage historiques, il n'y a pas d'élan pour améliorer la documentation. Même 
| si vous le faisiez, vous devriez backporter et patcher votre documentation pour 
| couvrir toutes les petites idiosyncrasies à travers les versions de noyau, et il 
| y en a beaucoup.
+-

+-#- Problèmes d'implémentation -#-
| 
| En travaillant avec BPF nous avons rencontré un certain nombre de problèmes 
| spécifiques à l'implémentation qui nous ont amenés à construire et publier ces 
| trois ([0], [1], [2]) outils BPF. Si vous êtes un défenseur, ou travaillez dans 
| la sécurité, et que vous considérez vous lancer avec BPF, voici une liste de 
| choses que vous voudrez probablement savoir. Présenté dans un ordre assez logique.
| 
| +-**- Le vérifieur craint, mais les alternatives sont pires. -**-
| | 
| | -...- Problème -...-
| | 
| | Vous allez rencontrer beaucoup de problèmes avec le vérifieur. Par exemple, 
| | quelle est la différence dans les deux extraits de code suivants ?
| | 
| | ```c
| | u32 *p = 1;
| | u32 i = *p;
| | ```
| | 
| | ```c
| | u32 *p = 1;
| | u32 i = NULL;
| | __builtin_memcpy(&i, p, sizeof(u32));
| | ```
| | 
| | Je vais vous le dire : le premier échoue au vérifieur, le deuxième non. Mais 
| | seulement parfois, excepté quand ça marche. Ce qui dépend de la version du 
| | noyau. Peut-être. Je veux dire, ils devraient compiler vers la même chose, 
| | pas vrai ? Apparemment non, et des différences subtiles peuvent complètement 
| | dérouter le vérifieur.
| | 
| | Le vrai problème avec le vérifieur est qu'il s'améliore tout le temps. Au fur 
| | et à mesure que les cas d'utilisation de BPF se stabilisent, les mainteneurs 
| | changent le vérifieur BPF pour mieux les supporter. Cela signifie que sur 
| | les anciennes versions de noyau, sans ces patches, vous devrez effectuer des 
| | contournements étranges pour faire fonctionner votre code avec les anciens 
| | vérifieurs.
| | 
| | Quelques autres problèmes de vérifieur que vous rencontrerez probablement en 
| | supportant une large gamme de versions de noyau :
| | 
| | - Le vérifieur déteste les boucles. Mais, parfois, il déteste aussi le 
| | déroulage de boucles. Si `clang` génère assez de sauts et gotos, même si vous 
| | lui dites de tout dérouler, le vérifieur pourrait (selon la version) l'échouer 
| | quand même. Le vérifieur doit être capable de garder une trace de toutes les 
| | branches et assurer une limite de profondeur maximale. S'il ne peut pas (que 
| | ce soit parce que vous bouclez ou parce que le vérifieur ne peut pas suivre) 
| | votre programme échouera à la vérification.
| | 
| | - Dans les anciennes versions de noyau (mais pas les nouvelles) les lectures 
| | et écritures de variables sont un grand non. Tous les offsets doivent être 
| | connus au moment de la compilation. Cela signifie que vous ne pouvez pas faire 
| | des choses comme définir `some_array[variable_index] = some_value`. Ceci, 
| | plus l'aversion pour les boucles, rend presque impossible la lecture de 
| | chaînes depuis la mémoire sur les noyaux sans la famille de helpers 
| | `read_str`. Le `qstr` du noyau implique un accès mémoire variable - et bonne 
| | chance pour trouver (ou définir) le terminateur nul par vous-même.
| | 
| | - Tout ce qui pourrait être un pointeur doit être vérifié comme nul. Si vous 
| | ne le faites pas, le vérifieur refusera de charger votre programme même si 
| | c'est sûr. Cela rend difficile de travailler avec des programmes qui pourraient 
| | s'attendre à une valeur nulle. La convention qui plaît le plus au vérifieur 
| | est de retourner immédiatement après une vérification nulle échouée, et 
| | contourner ceci est délicat et implique des essais et erreurs.
| | 
| | Il y a des alternatives au vérifieur du noyau, comme PREVAIL[8], mais elles 
| | ont leur propre ensemble de problèmes. Pour ce que ça vaut, PREVAIL est un 
| | projet impressionnant et Microsoft basera son vérifieur BPF Windows dessus. 
| | Mais, malheureusement, il ne correspond pas au comportement attendu du 
| | vérifieur noyau. Juste parce que quelque chose passe PREVAIL ne signifie pas 
| | qu'il passera le vérifieur noyau. Juste parce que quelque chose échoue à 
| | PREVAIL ne signifie pas qu'il échouera au vérifieur noyau (même si ça 
| | devrait probablement). 
| | 
| | -...- Solution -...-
| | 
| | **Exécutez tôt, exécutez souvent, exécutez partout.** Votre environnement de 
| | développement devrait rendre aussi facile que possible de tester votre code 
| | sur tous les noyaux que vous devez supporter (ou aussi proche d'un échantillon 
| | représentatif que vous pouvez obtenir). La seule façon de savoir si le 
| | vérifieur noyau acceptera votre programme est de l'exécuter à travers le 
| | vérifieur noyau, le vrai vérifieur noyau, sur le noyau spécifique que vous 
| | ciblez. Notez que cela signifie le noyau spécifique à la distro, avec toutes 
| | leurs modifications et backports. Par exemple, les anciens noyaux Enterprise 
| | Linux (red hat, centos, et ainsi de suite) (2.x et 3.x) ont backporté des 
| | fonctionnalités BPF qui pourraient vous surprendre, puisqu'elles ne 
| | correspondent pas aux numéros de version du noyau principal. La seule façon 
| | de savoir ce qui est supporté est d'essayer.
| | 
| | **Activez les logs.** Celle-ci vient avec un avertissement. Vous devez fournir 
| | au vérifieur un grand tampon mémoire pour écrire ses logs de vérification. Si 
| | vous ne lui donnez pas assez d'espace, il échouera la vérification, même si 
| | le programme passerait autrement. Si vos programmes sont complexes, assurez-vous 
| | que votre tampon est suffisamment grand (mais pas trop grand, ou le chargement 
| | prendra une éternité) et soyez sûr de désactiver les logs du vérifieur en 
| | production pour éviter des problèmes avec des programmes échouant à se charger 
| | quand vous savez qu'ils le devraient.
| | 
| | **Les messages d'erreur que vous obtenez sembleront cryptiques au début.** Le 
| | vérifieur BPF utilise beaucoup de terminologie et a beaucoup de restrictions 
| | qui ne sont pas documentées (bien sûr) que vous apprendrez avec le temps. Si 
| | vous êtes bloqué, l'issue tracker du repo GitHub de la BPF Compiler Collection 
| | (BCC)[9] est une excellente ressource. Vous pouvez probablement trouver un 
| | ticket Brendan Gregg qui passe au moins par la classe générale de l'erreur 
| | que vous obtenez.
| +-
|  
| +-**- BPF n'existe pas vraiment. -**-
| | 
| | -...- Problème -...-
| | 
| | BPF est vraiment juste un jeu d'instructions, pour lequel le noyau Linux fournit 
| | une VM, un vérifieur, et quelques fonctions d'aide. Vous exécutez vos programmes 
| | dans ce contexte d'exécution, et appelez les fonctions d'aide pour étendre les 
| | capacités de la VM. Lorsque vous écrivez un programme BPF, ce que vous écrivez 
| | vraiment est un kprobe, ou un uprobe, ou un classificateur eXpress Data Path 
| | (XDP), ou un classificateur Traffic Control (TC), ou un des nombreux autres 
| | types de programmes kernelspace qui ont été déportés vers le sous-système BPF. 
| | Il y a une tonne de types de programmes BPF et d'autres sont ajoutés tout le 
| | temps, pour une variété de cas d'utilisation. Il s'avère que pouvoir exécuter 
| | du code en sécurité dans le noyau permet beaucoup de fonctionnalités 
| | intéressantes et utiles. Malheureusement, chaque type de programme a sa propre 
| | façon de se charger, exécuter, et nettoyer après lui, la plupart n'étant pas 
| | du tout documentée.
| | 
| | Sur certaines distros, les outils dont vous aurez besoin pour charger ces 
| | programmes pourraient ne pas être activés par défaut. Par exemple, certaines 
| | distros ne montent pas automatiquement `debugfs`, dont vous aurez besoin pour 
| | charger des kprobes sur les anciens noyaux. 
| | 
| | Lorsque vous finissez par comprendre comment charger votre programme, l'ABI pour 
| | définir les programmes est entièrement basé sur une convention implicite et non 
| | documentée. Par exemple, vous verrez beaucoup de `SEC("kprobe/my_kprobe")` pour 
| | dire au loader que vous chargez un kprobe. 
| | 
| | ```c
| | /* helper macro to place programs, maps, license in
| |  * different sections in elf_bpf file. Section names
| |  * are interpreted by elf_bpf loader
| |  */
| | #define SEC(NAME) __attribute__((section(NAME), used))
| | ```
| | 
| | Ceci est en fait complètement inutile, au niveau syscall, et est simplement une 
| | convention commune. Comme vous pouvez le voir dans l'extrait ci-dessus, c'est 
| | juste une macro pour définir le nom de section dans l'exécutable ELF compilé. 
| | Il n'y a rien de spécifique à BPF là-dedans. Donc vous ne devez pas seulement 
| | connaître les exigences du type de programme que vous essayez de charger, mais 
| | aussi les conventions utilisées par les outils qui le chargent et l'exécutent.
| | 
| | -...- Solution -...-
| | 
| | Déterminez ce que vous voulez que votre programme fasse d'abord. Voulez-vous 
| | de la visibilité dans le noyau ? Alors vous voudrez probablement un kprobe ou 
| | tracepoint. Voulez-vous supprimer des paquets entrants ? Vous voulez probablement 
| | XDP. Voulez-vous construire des détections sur le trafic sortant ? Vous pourriez 
| | vouloir TC, ou vous pourriez vouloir un kprobe dans la pile réseau du noyau. 
| | Déterminez ça, puis déterminez ce dont vous aurez besoin pour l'exécuter comme 
| | vous voulez l'exécuter (one off ? daemon ?). Lorsque nous avons fait `oxidebpf` 
| | nous avons dû optimiser pour la stabilité dans les fonctionnalités dont nous 
| | avions le plus besoin (par ex., kprobes) plutôt que la couverture de tous les 
| | différents types de programmes BPF.
| | 
| | Si vous ne pouvez pas trouver de bibliothèques adaptées à vos besoins pour le 
| | type de programme choisi, vous devrez probablement l'écrire vous-même (ou y 
| | contribuer dans un projet open source). Parce que tout est mal documenté, vous 
| | devrez creuser beaucoup de code source pour mettre ensemble le véritable 
| | ensemble de fonctionnalités nécessaires. Les bibliothèques quasi-officielles 
| | comme libbpf et libbcc tendent à fonctionner le mieux, mais il y a des 
| | problèmes là-bas (que nous allons aborder).
| | 
| | Je recommande vivement d'utiliser `bpftool` pour le débogage pendant le 
| | développement. Il fournit la vue la plus facile à utiliser sur quels 
| | programmes et maps sont chargés et où. Il vous laisse visualiser des données 
| | dans les maps, dumper des programmes, et plus. Le seul problème avec 
| | `bpftool` est qu'il n'est jamais dans le même paquet. Certaines distros et 
| | repos vous laissent l'installer avec un `yum install bpftool`. D'autres 
| | nécessitent que vous fassiez `apt-get install linux-oem-tools`. Parfois vous 
| | avez besoin de `apt-get install linux-oem-tools-`uname -r``. Ça dépend. 
| | Quoi que vous exécutiez, cependant, vous voudrez probablement avoir cet outil 
| | installé.
| +-
|  
| +-**- J'espère que vous trouvez les contraintes amusantes. -**-
| | 
| | -...- Problème -...-
| | 
| | Êtes-vous l'une des douzaines de personnes déraisonnablement contrariées que 
| | `0x10c`[10] n'ait jamais été released ? Moi aussi ! Je trouve que travailler 
| | dans des contraintes est difficile et agréable. Et laissez-moi vous dire, les 
| | programmes BPF ont beaucoup de contraintes. 
| | 
| | Vous obtenez 512 octets d'espace pile pour votre programme, un demi kilo-octet. 
| | Cela n'apparaît pas comme quelque chose qui a ou aura jamais changé. Il est 
| | également unclear si cela s'applique aux tail calls. Certaine documentation 
| | implique que les tail calls utilisent le même espace pile, donc vous êtes 
| | limité à 512 octets au total, mais en pratique il semble être de 512 octets 
| | par programme. Et `clang` ne pourra probablement pas vous aider. Les programmes 
| | BPF, pour une raison quelconque, n'aiment pas récupérer l'espace pile. Vos 
| | variables seront hissées et instanciées au début de l'exécution. Si vous 
| | voulez faire des choses comme dumper les arguments de syscall ou `pt_regs`, 
| | surtout lorsque vous travaillez avec des chaînes, vous vous retrouverez à 
| | manquer d'espace pile très rapidement. 
| | 
| | Il y a une limite d'instructions pratique d'environ 4096 instructions. La 
| | limite d'instructions dans le passé était définie (pour autant que je puisse 
| | le dire) en fonction de ce que le vérifieur pouvait vérifier avant de déclarer 
| | "ça a assez duré, je ne peux pas vérifier que ça ne va pas s'arrêter, donc je 
| | vais l'échouer." Vous pouvez obtenir plus d'instructions en manipulant le 
| | vérifieur, et en faisant d'autres astuces que vous trouverez dans les listes 
| | de diffusion, si vous voulez vraiment mettre l'effort. Les nouveaux vérifieurs 
| | vous laissent obtenir jusqu'à 1 000 000 d'instructions, mais cela ne vous 
| | aidera que si vous supportez des noyaux plus récents.
| | 
| | -...- Solution -...-
| | 
| | Pour contourner la limite d'instructions, vous pouvez utiliser des tail calls. 
| | Les tail calls sont le plus proche d'un véritable appel de fonction que BPF 
| | ait. Vous transférez le flux vers le programme que vous appelez. Vous pouvez 
| | enchaîner les tail calls comme ça ensemble jusqu'à 33 fois. Il y a quelques 
| | avertissements, que nous aborderons plus tard.
| | 
| | Il y a quelques astuces que vous pouvez utiliser pour contourner la limite de 
| | pile. Une astuce est de réutiliser explicitement l'espace pile. Par exemple, 
| | réutiliser des variables ou instancier une structure d'octets pour agir comme 
| | votre espace scratch et réutiliser manuellement les offsets à l'intérieur. 
| | Une autre astuce est de construire votre propre pile avec des maps. Sur 
| | certaines versions de noyau vous pouvez demander une structure depuis une map 
| | et obtenir un pointeur vers celle-ci. Si la structure demandée n'existe pas 
| | (par ex., le tableau de maps à l'index demandé était vide) vous obtiendrez 
| | toujours un pointeur vers une structure vide que vous pouvez manipuler. 
| | D'autres versions de noyau nécessitent que cette map-struct soit copiée vers 
| | la pile avant d'être modifiée, donc votre expérience peut varier.
| | 
| | Avec tout ça dit, je veux offrir quelques conseils pratiques. Si l'information 
| | que vous récupérez est trop grande pour tenir sur la pile, vous devriez 
| | simplement l'envoyer au fur et à mesure que vous la lisez. Créez un type de 
| | messagerie et un pipeline pour le découpage et la reconstruction des données 
| | dans l'espace utilisateur, copiez autant que vous pouvez vers la pile, puis 
| | envoyez-la à travers une map. Cela fonctionnera sur une plus large gamme de 
| | versions de noyau, et vous n'aurez pas à vous soucier de si votre noyau hôte 
| | permet de manipuler et émettre directement la mémoire de map. Vous pouvez la 
| | reconstruire dans l'espace utilisateur à volonté. C'est ce que des entreprises 
| | comme Google font pour leur télémétrie BPF. 
| +-
|  
| +-**- Les bonnes choses sont GPL. -**-
| | 
| | -...- Problème -...-
| | 
| | Toutes les fonctions d'aide utiles (comme `perf_event_output`[6]) sont 
| | exportées comme GPL-only. Si vous voulez que votre programme fasse quelque 
| | chose d'utile, vous allez devoir le licensier sous GPL. Cela rend difficile 
| | de faire des programmes propriétaires basés sur BPF. Si votre programme est 
| | seulement interne, et jamais distribué, vous allez bien. Mais si vous commencez 
| | à distribuer vos programmes (à des clients, amis, où que ce soit) vous devez 
| | le publier sous GPL.
| | 
| | -...- Solution -...-
| | 
| | Réponse courte : Rendez le monde meilleur, releasez votre code et outils BPF.
| | 
| | Réponse longue : BPF est toujours une discipline de niche et complexe, donc 
| | open sourcer votre outillage ne réduit pas l'efficacité compétitive pour une 
| | entreprise. D'un point de vue individuel, open sourcer votre outillage fait 
| | connaître votre nom et vous rend plus valuable en tant qu'employé. D'un point 
| | de vue employeur, plus BPF devient accessible, plus il sera facile d'embaucher 
| | des gens pour le construire et le maintenir. D'un point de vue communautaire, 
| | nous pouvons tous apprendre les uns des autres en travaillant en ouvert. 
| | Peut-être avez-vous un cas d'utilisation intéressant que les mainteneurs 
| | d'autres bibliothèques aimeraient connaître, ou pourraient offrir des conseils 
| | à ce sujet. Tout le monde gagne.
| +-
|  
| +-**- Par défaut, vous obtenez le défaut. -**-
| | 
| | Sinon, BPF n'est bon avec les conteneurs que si vous lui dites de l'être.
| | 
| | -...- Problème -...-
| | 
| | Faites attention aux hypothèses que vous faites sur l'information que vous 
| | récupérez depuis un programme BPF. Si vous récupérez le code de retour d'un 
| | appel `fork`, il va vous donner le code de retour de l'appel `fork` : le pid 
| | dans le namespace du processus appelant. Peut-être est-ce ce que vous vouliez, 
| | ou peut-être que vous vouliez vraiment le pid du processus enfant non-namespacé. 
| | Peut-être demandez-vous au programme BPF de rassembler le pid (avec le helper 
| | `get_pid_tgid`). Vous prenez les 32 bits supérieurs, correspondant au pid, mais 
| | rien ne correspond. Eh bien, vous exécutez dans l'espace noyau ce qui signifie 
| | que le `pid` que vous voulez probablement est en fait le `tgid`, et ce que vous 
| | avez obtenu est un `tid`. À moins que vous vouliez un `tid`, auquel cas vous 
| | devriez obtenir le `pid`. La compréhension kernelspace d'un `pid` n'est pas la 
| | même que la compréhension userspace d'un `pid`. Si vous voulez identifier un 
| | fichier, vous voulez probablement le numéro d'inode et le numéro de périphérique, 
| | un descripteur de fichier ne sera pas aussi utile.
| | 
| | -...- Solution -...-
| | 
| | Si vous voulez que votre programme récupère des informations, pensez à quelles 
| | informations vous devez récupérer. Assurez-vous de savoir où cette information 
| | existe (quelles structures, où elles vivent en mémoire, et comment y arriver) 
| | puis trouvez un endroit (en supposant que vous lancez un kprobe) dans le noyau 
| | où vous pouvez attacher votre programme aussi près de cette information que 
| | possible. Par exemple, si vous avez vraiment besoin du pid du namespace root 
| | du processus enfant de fork, vous voulez probablement hooker quelque part dans 
| | le chemin du nouveau processus enfant pour que vous puissiez récupérer le 
| | `pid` depuis le `task_struct`. 
| | 
| | Soyez conscient que cet emplacement pourrait changer entre les versions de 
| | noyau, ou l'information pourrait prendre une forme différente. Vous devrez peut-être 
| | choisir un point de sonde moins optimal qui est disponible sur plus de systèmes. 
| | Ou vous devrez peut-être changer l'information que vous rassemblez pour quelque 
| | chose d'autre qui existe sur tous les noyaux que vous supportez. Cela nous mène 
| | aux deux prochains problèmes.
| +-
|  
| +-**- CO-RE (probablement) ne vous aidera pas. -**-
| | 
| | -...- Problème -...-
| | 
| | Les mainteneurs ajoutent constamment des fonctionnalités pour aider les 
| | développeurs BPF à compiler une fois exécuter partout leurs programmes BPF. 
| | Malheureusement, vous vous retrouverez probablement à essayer de cibler des 
| | versions de noyau qui n'ont pas ces fonctionnalités. Ou, si vous le faites, 
| | puisque ces fonctionnalités sont ajoutées petit à petit, il se peut qu'elles 
| | n'aient pas toutes les fonctionnalités CO-RE auxquelles vous vous attendez.
| | 
| | Par exemple, la fonctionnalité BTF permet de référencer les membres de struct 
| | directement, même s'ils ont été compilés dans une disposition randomisée, à 
| | travers différentes versions de noyau, et sans recompiler. Cette fonctionnalité 
| | a été ajoutée en avril 2018[11]. Vous aurez probablement besoin d'écrire du 
| | code pour des noyaux d'avant avril 2018. Cela signifie que quelque chose comme 
| | `current->real_parent->pid` n'est pas garanti de fonctionner sans 
| | recompiler pour (ou sur) l'hôte.
| | 
| | -...- Solution -...-
| | 
| | Il n'y a vraiment pas de moyen de contourner celui-ci. C'est ce que nous 
| | faisons, Microsoft le fait aussi pour leurs machines Linux, et je suis sûr 
| | qu'il y en a d'autres. D'abord, vous déterminez les offsets des membres de 
| | struct pour votre version de noyau désirée puis vous les chargez 
| | dynamiquement dans votre programme BPF au runtime. Par exemple, cet extrait 
| | de code de [12] montre comment nous lisons les offsets de struct depuis une 
| | map et les utilisons dans notre `bpf_probe_read` pour récupérer des valeurs.
| | 
| | ```c
| | static __always_inline int read_value(
| | 		void *base, u64 offset, void *dest, size_t dest_size
| | )
| | {
| |     /* null check the base pointer first */
| |     if (!base)
| |         return -1;
| | 
| |     u64 _offset = (u64)bpf_map_lookup_elem(&offsets, &offset);
| |     if (_offset)
| |     {
| |         return bpf_probe_read(dest, dest_size, base + *(u32 *)_offset);
| |     }
| |     return -1;
| | }
| | ```
| | 
| | Pour trouver ces valeurs d'offset en premier lieu, nous avons construit le 
| | `linux-kernel-component-cloud-builder`, ou `LKCCB`, qui construit des centaines 
| | sinon des milliers de modules noyau avec le debug activé pour toutes nos 
| | versions de noyau cibles et extrait les informations d'offset de structure 
| | depuis l'info debug DWARF du LKM[1].
| +-
|  
| +-**- Les interfaces stables ne le sont pas. -**-
| | 
| | -...- Problème -...-
| | 
| | Vous trouverez souvent, en travaillant avec le noyau, qu'il n'y a pas autant 
| | d'interfaces stables que vous pensiez. Même les syscalls, qui sont censés être 
| | une grande partie de l'interface utilisateur stable, ne sont pas nécessairement 
| | stables. 
| | 
| | Par exemple, si vous avez voyagé dans le temps et vouliez monitorer les forks 
| | de processus, vous sondez le syscall `fork`. Ça marcherait bien pendant un 
| | moment, jusqu'à ce que `clone` soit introduit. Si vous avez arrêté de prêter 
| | attention, vous perdriez vos données complètement lorsque glibc (et tout ce 
| | qui va avec) a changé `fork()` pour être un wrapper autour de `clone()`.
| | 
| | Peut-être voulez-vous obtenir les arguments d'un syscall. Ça devrait être 
| | facile, on vous donne `pt_regs`, accédez simplement aux registres qui 
| | contiennent les arguments ! Sauf si vous êtes sur x86_64, et sur un noyau 
| | plus ancien que 4.17, vous aurez probablement les `pt_regs` de la fonction 
| | wrapper syscall, qui appelle à son tour la vraie fonction syscall. Et bien 
| | sûr, tout se réorganise si vous avez besoin d'ajouter le support aarch64, qui 
| | a son propre ensemble de conventions d'appel.
| | 
| | Parfois un symbole marqué comme exporté ne peut pas être attaché, presque 
| | inexplicablement. C'est généralement dû à GCC inlinant la fonction, et le 
| | symbole étant renommé en quelque chose comme `symbol_name.part.1213`. Essayer 
| | de binder `symbol_name` ne fonctionnera pas.
| | 
| | -...- Solution -...-
| | 
| | Pour différentes architectures vous pouvez probablement vous en sortir avec 
| | des macros qui compilent conditionnellement selon l'architecture que vous 
| | ciblez, puis construire une copie par architecture. Pour les wrappers syscall, 
| | vous pouvez faire quelque chose de similaire mais construire en ciblant 
| | différentes versions de noyau. En pratique, vous pourriez trouver que vous 
| | avez besoin de nombreuses variantes et copies d'un seul programme, toutes avec 
| | de légères différences, pour supporter différents noyaux et architectures.
| | 
| | Pour le problème de nom de symbole, cela revient à exécuter tôt et exécuter 
| | souvent. Ça vaut souvent le coup de monter une VM de quelques-uns des noyaux 
| | que vous ciblez et de vérifier doublement que les emplacements que vous hookez 
| | sont bien dans `/proc/kallsyms`. Parfois vous trouverez que les fonctions que 
| | vous regardiez n'existent pas dans différentes versions, ou ont été renommées 
| | et déplacées. Je recommande de vous mettre à l'aise avec le référentiel 
| | croisé Elixir de Bootlin (mais vous devez toujours exécuter et voir, parce que 
| | les distros font leurs propres backports qui ne correspondront pas à ce qui 
| | est dans le référentiel croisé principal).
| +-
|  
| +-**- Exécuter des programmes BPF comme prévu implique de la magie. -**-
| | 
| | -...- Problème -...-
| | 
| | Si vous utilisez libbcc, libbpf, bpftrace, ou tout autre outil BPF haut niveau 
| | vous remarquerez rapidement qu'ils font beaucoup de magie pour vous. BCC 
| | (l'interface python) va plus ou moins réécrire vos programmes pour qu'ils 
| | fonctionnent sur votre système hôte. Vous allez vous retrouver à obtenir des 
| | messages d'erreur sur du code que la bibliothèque a écrit pour vous. Ils vous 
| | aident également à contourner les limitations CO-RE en compilant sur l'hôte, 
| | et en utilisant différentes astuces et bricolages pour faire fonctionner le 
| | même code de programme dans de nombreux environnements aussi proprement que 
| | possible. Cela n'aide pas beaucoup quand vous avez besoin de construire et 
| | distribuer de véritables programmes BPF bruts dans leur propre fichier ELF.
| | 
| | Ces bibliothèques sont également assez alambiquées. Il y a beaucoup de 
| | chevauchement dans les mainteneurs entre ces bibliothèques et les gens qui 
| | travaillent sur BPF dans le noyau, donc documenter les interactions n'est pas 
| | une priorité. Mais vous n'avez pas réellement besoin de tout ce que ces 
| | bibliothèques font. Après un moment, surtout avec la réécriture, vous allez 
| | vous retrouver à vouloir écrire et charger du code C BPF pur. Voici un extrait 
| | d'une map que j'ai mise ensemble en essayant de comprendre quels syscalls 
| | étaient réellement faits lorsque libbpf chargeait un programme.
| | 
| | ```
| | KProbe
| |   |-> bpf_attach_kprobe()
| |       |-> bpf_attach_probe()
| |           |-> bpf_try_perf_event_open_with_probe()
| |               |-> bpf_find_probe_type()
| |               |-> bpf_get_retprobe_bit()
| |               |-> syscall(__NR_perf_event_open)
| |           |-> create_probe_event()
| |               |-> enter_mount_ns()
| |                   |-> setns()
| |               |-> exit_mount_ns()
| |                   |-> setns()
| |           |-> bpf_attach_tracing_event()
| |               |-> ioctl( PERF_EVENT_IOC_SET_BPF )
| |               |-> ioctl( PERF_EVENT_IOC_ENABLE )
| |           |-> bpf_close_perf_event_fd()
| |               |-> ioctl( PERF_EVENT_IOC_DISABLE )
| | ```
| | 
| | Ces bibliothèques sont également GPL, ce qui signifie que votre programme 
| | userspace serait également licensié sous GPL et pas seulement vos programmes 
| | BPF. Aussi génial que cela soit pour les utilisateurs, si vous travaillez pour 
| | une entreprise qui aime faire de l'argent vous pourriez ne pas être autorisé 
| | à toucher à GPL. Cela pourrait même être dans votre contrat.
| | 
| | -...- Solution -...-
| | 
| | Si vous écrivez des programmes BPF complexes pour la sécurité, vous voudrez 
| | probablement l'écrire en C sans l'"aide" de quelque chose comme BCC. Vous 
| | voudrez également un peu plus de contrôle et transparence en chargeant et 
| | attachant vos programmes. Dans mon expérience, libbpf n'était pas géniale 
| | pour nettoyer après lui-même et c'est devenu frustrant.
| | 
| | Utilisez une bibliothèque propre, simple, construite depuis le sol pour charger 
| | BPF dans votre langage de choix. Pour Rust, `aya`[16] est une bonne, et j'ai 
| | travaillé sur `oxidebpf`[0]. Golang a également de bonnes options. Un thème 
| | commun de ces projets est la quantité d'effort qui est entrée dans le reverse 
| | engineering de la logique de chargement de programme non documentée et sa 
| | réimplémentation. Profitez de ce travail et utilisez-le pour charger vos 
| | programmes. Ils sont également licensiés de manière permissive !
| +-
|  
| +-**- La vitesse tue. -**-
| | 
| | -...- Problème -...-
| | 
| | Après vous être lancé dans BPF, vous pourriez benchmarker quelques-uns de vos 
| | programmes et être surpris de combien BPF est plus rapide que ce que vous 
| | utilisiez avant, comme audit. Cela rend très tentant de tracer et sonder plus 
| | que vous ne le devriez probablement. Par exemple, si vous voulez tracer les 
| | fermetures de socket vous pourriez être tenté de mettre un kprobe sur le 
| | syscall `close`. Ce syscall est appelé tout le temps, et le sonder ralentira 
| | votre système inutilement. La plupart des messages seront discardés puisque 
| | vous ne vous souciez que des sockets. Il y a beaucoup d'autres zones 
| | intéressantes qui ne peuvent pas être raisonnablement instrumentées en raison 
| | de l'impact sur les performances. 
| | 
| | -...- Solution -...-
| | 
| | Tracez seulement ce dont vous avez besoin, et réduisez la portée autant que 
| | possible. En reprenant l'exemple de `close`, vous seriez mieux de sonder 
| | quelque part en aval où les fonctions `tcp_close` ou `udp_close` individuelles 
| | sont appelées.
| | 
| | ```
| | struct proto tcp_prot = {
| | 	// ...
| | 	.close			= tcp_close,
| | 	// ...
| | };
| | EXPORT_SYMBOL(tcp_prot);
| | 
| | struct proto udp_prot = {
| | 	// ...
| | 	.close			= udp_lib_close,
| | 	// ...
| | };
| | EXPORT_SYMBOL(udp_prot);
| | ```
| | 
| | Le livre de Brendan Gregg[7], encore une fois, a un excellent tableau qui 
| | montre l'impact global sur les performances du tracing de différents points 
| | dans le noyau. Vous pourriez aussi simplement raisonner intuitivement sur à 
| | quelle fréquence vous pensez que chaque zone que vous voulez sonder est 
| | exercée. Plus un chemin de code est couramment exécuté, plus il sera coûteux 
| | de le sonder.
| | 
| | Même après avoir fait de votre mieux pour réduire la portée et optimiser vos 
| | programmes BPF, vous voudrez probablement exécuter des benchmarks pendant que 
| | vous ajustez les choses pour voir ce qui performe le mieux dans votre 
| | environnement cible. Les flamegraphs[13] sont un excellent moyen de voir 
| | d'où vient la plupart de votre overhead, surtout si combinés avec un 
| | benchmakeur comme UnixBench[14]. Les résultats pourraient vous surprendre. 
| | 
| | Je recommande également de traiter les événements BPF en batches. Vous allez 
| | probablement envoyer beaucoup d'informations à travers des maps qui doivent 
| | être lues depuis l'espace utilisateur. Si vous obtenez des informations trop 
| | grandes pour la pile, les informations seront envoyées en morceaux qui doivent 
| | être reconstruits dans l'espace utilisateur. Il est certainement possible de 
| | boucler un poll+read bloquant sur le perfmap ou le ring buffer BPF, mais faire 
| | ça résultera en un overhead significatif. Vous êtes beaucoup mieux de laisser 
| | les tampons se remplir un peu, et les traiter en batches (traitez par batch, 
| | ne streamez pas). Faire ça m'a donné des gains de performance significatifs 
| | dans les benchmarks pour les programmes BPF que j'écris au travail.
| +-
|  
| +-**- Ne Paniquez Pas. -**-
| 
| | -...- Problème -...-
| | 
| | Les programmes BPF vivront généralement aussi longtemps que quelque chose 
| | détient un descripteur de fichier qui pointe vers eux. Cependant, parfois 
| | vous devez nettoyer après eux manuellement (comme en utilisant `debugfs`). 
| | Si votre programme userspace crash ou panic, les choses pourraient ne pas 
| | être nettoyées correctement. Cela peut mener à toutes sortes de problèmes 
| | quand vous redémarrez vos sondes, comme recevoir des événements dupliqués. 
| | 
| | Si vous construisez des outils de courte durée, one shot, c'est moins d'une 
| | préoccupation. Mais si vous gérez plusieurs sondes dans le cadre d'un daemon 
| | de monitoring de longue durée alors c'est quelque chose dont vous devez être 
| | prudent.
| | 
| | -...- Solution -...-
| | 
| | Assurez-vous de concevoir le composant userspace du programme BPF pour garder 
| | vos programmes en vie aussi longtemps que vous en aurez besoin. Gérez 
| | gracieusement toutes les erreurs dans le thread qui garde vos programmes BPF 
| | en vie et assurez-vous de nettoyer après vous en cas d'échec ou d'arrêt. 
| | Gardez à l'esprit que beaucoup d'anciens outils BPF sont construits autour 
| | de programmes de courte durée, destinés à des choses comme `bpftrace` ou le 
| | débogage en production. 
| +-
|  
| +-**- Connaissez vos limites. -**-
| | 
| | -...- Problème -...-
| | 
| | Votre programme aura des instructions et utilisera probablement des maps. Cela 
| | prend de la place, que le syscall BPF va commodément memlock pour vous. Sur 
| | beaucoup de distros, c'est bon. Sur d'autres, cependant, le ulimit memlock 
| | par défaut est assez bas[15]. Voir la sortie suivante de `ulimit -l` sur 
| | différentes distributions.
| | 
| | ```
| | vagrant@ubuntu2004:~$ ulimit -l
| | 65536
| | [vagrant@centos7 ~]$ ulimit -l
| | 64
| | vagrant@opensuse15:~> ulimit -l
| | 64
| | ```
| | 
| | Si vous ne pouvez pas memlock assez de mémoire pour vos instructions et maps, 
| | vous serez rejeté avec des messages d'erreur de vérifieur cryptiques.
| | 
| | -...- Solution -...-
| | 
| | Calculez la quantité de mémoire dont vos programmes et maps auront besoin, 
| | et vérifiez les limites memlock sur vos systèmes cibles. Vous pouvez être 
| | bon, ou vous devrez peut-être l'augmenter d'abord. Certaines bibliothèques 
| | (comme celle que nous avons écrite ![0]) peuvent essayer de s'occuper de ça 
| | pour vous. 
| +-
|  
| +-**- Les tail calls ne sont pas garanties. -**-
| | 
| | -...- Problème -...-
| | 
| | Pensez aux tail calls comme l'équivalent BPF de `execve`, excepté moins 
| | puissant. Il commencera à exécuter une nouvelle sonde, avec l'argument de 
| | contexte original, et remplacera tout ce que vous faisiez précédemment. Vous 
| | ne pouvez pas lui fournir d'arguments personnalisés, et le tail call doit 
| | passer le vérifieur indépendamment. Cela signifie que si vous voulez 
| | communiquer entre tail calls vous aurez besoin d'utiliser des maps. Vous êtes 
| | également limité à enchaîner 33 tail calls dans une seule exécution, après 
| | cela l'exécution de tail call se terminera simplement.
| | 
| | Vous ne pouvez pas appeler dans un autre programme avec un tail call 
| | directement, soit. Vous avez besoin de référencer un index dans une map de 
| | programme tail call (un type de map BPF) qui doit être défini depuis 
| | l'espace utilisateur. Par exemple, si vous voulez faire un tail call de 
| | `prog_a()` vers `prog_b()`, vous devrez d'abord charger `prog_a()` et 
| | `prog_b()`. À ce moment si `prog_a()` se déclenche, le tail call vers 
| | `prog_b()` va échouer. Puis, depuis l'espace utilisateur, vous avez besoin 
| | de mettre à jour une map pour dire "`prog_b()` est à l'index 5, si quelqu'un 
| | essaie de faire un tail call vers l'index 5, envoyez-le vers `prog_b()`."
| | Suivre et maintenir tous ces index peut être lourd.
| | 
| | Et il n'y a pas toujours de garantie que le tail call se déclenchera. Vous 
| | pourriez atteindre une limite d'exécution, ou une limite de mémoire, ou un 
| | autre cas limite étrange du vérifieur qui empêche le tail call de se 
| | déclencher. Vos programmes doivent gérer ça gracieusement.
| | 
| | -...- Solution -...-
| | 
| | D'abord, vous devrez écrire vos tail calls comme si elles étaient des 
| | programmes indépendants. Pensez à concevoir chacun d'eux pour récupérer un 
| | bit différent d'information que vous cherchez. Si vous vous retrouvez à 
| | recalculer les mêmes choses dans chaque programme ou avez autrement besoin 
| | de communiquer à travers les appels, stockez et récupérez des informations 
| | depuis une map.
| | 
| | Pour gérer les index, utilisez un enum pour vos tail calls et référez-vous 
| | depuis votre application userspace. Par exemple, ayez un `enum tail_calls 
| | { PROBE_A, PROBE_B };` puis référez-vous depuis l'intérieur de vos programmes 
| | et lors du chargement de la map de programme depuis l'espace utilisateur. Le 
| | descripteur de fichier pour `probe_a()` va à l'index `PROBE_A`, et ainsi de 
| | suite. Si vous voulez appeler dans `probe_a()`, vous y arrivez en demandant 
| | `PROBE_A` avec `bpf_tail_call(ctx, &tail_call_table, PROBE_A);`.
| | 
| | Votre programme devrait également avoir un plan pour ce qui se passe si le 
| | tail call ne se produit pas. Voulez-vous envoyer une erreur ? L'ignorer ? 
| | Envoyer un message que l'exécution a été complétée ? Quelque chose d'autre ? 
| | Par exemple, si vous utilisez des tail calls récursifs pour lire une valeur 
| | de chaîne vous pourriez vouloir retourner un message qui dit que vous avez 
| | atteint votre limite de tail call avant d'avoir fini de lire la chaîne.
| +-
| 
| +-**- Vous ne pouvez pas simplement retourner ce que vous voulez. -**-
| 
| | Sinon, vous êtes seul avec la gestion d'erreur.
| | 
| | -...- Problème -...-
| |
| | Celui-ci était un problème que nous n'avions même pas réalisé que nous avions 
| | parce qu'il était si subtil. En C c'est assez coutumier de retourner `0` en 
| | succès et `-1` (ou un autre code d'erreur négatif) en cas d'échec. La valeur 
| | retournée est généralement écrite dans un tampon ou un autre pointeur donné 
| | comme paramètre de fonction. Vous vérifiez le code de retour pour le succès 
| | ou l'échec et prenez les actions appropriées (en théorie). En écrivant des 
| | programmes BPF en C, surtout des kprobes, vous pourriez être tenté de suivre 
| | ce modèle. Après tout, ça a du sens. La valeur réelle que vous retournez est 
| | envoyée via perf ou écrite dans une map pour que l'espace utilisateur la 
| | récupère, donc la valeur de retour de la sonde elle-même devrait être `0` 
| | pour indiquer le succès ou `-1` pour indiquer l'échec, pas vrai ? Juste 
| | comme tous les autres programmes C ? Faux ! Pour les types de programmes 
| | autres que les kprobes (rappelez-vous, BPF est juste un environnement 
| | d'exécution) c'est plus évident que les codes de retour ont une signification 
| | spéciale. Par exemple, les programmes XDP ont des codes de retour explicites 
| | pour supprimer, passer, ou retraiter les paquets.
| | 
| | Pour les kprobes, `return 0;` signifie "j'ai fini avec ce kprobe, vous pouvez 
| | continuer." Vous indiquez que vous voulez garder la sonde en place avec 
| | _littéralement tout autre code de retour_ (y compris `return -1;`). Ce n'est 
| | probablement pas ce que vous voulez. Regardez cette fonction depuis le 
| | handler kprobe dans [18] :
| | 
| | ```c
| | /* Kprobe profile handler */
| | static int
| | kprobe_perf_func(struct trace_kprobe *tk, struct pt_regs *regs)
| | {
| | 	// ...
| | 	if (bpf_prog_array_valid(call)) {
| | 		// ...
| | 		ret = trace_call_bpf(call, regs);
| |		// ...
| | 		if (!ret)
| | 			return 0;
| | 	}
| | 
| | 	head = this_cpu_ptr(call->perf_events);
| | 	if (hlist_empty(head))
| | 		return 0;
| | 
| | 	dsize = __get_data_size(&tk->tp, regs);
| | 	__size = sizeof(*entry) + tk->tp.size + dsize;
| | 	size = ALIGN(__size + sizeof(u32), sizeof(u64));
| | 	size -= sizeof(u32);
| | 
| | 	entry = perf_trace_buf_alloc(size, NULL, &rctx);
| | 	if (!entry)
| | 		return 0;
| | 
| | 	entry->ip = (unsigned long)tk->rp.kp.addr;
| | 	memset(&entry[1], 0, dsize);
| | 	store_trace_args(&entry[1], &tk->tp, regs, sizeof(*entry), dsize);
| | 	perf_trace_buf_submit(entry, size, rctx, call->event.type, 1, regs,
| | 			      head, NULL);
| | 	return 0;
| | }
| | ```
| | 
| | Il y a deux choses que vous devriez remarquer dans cet extrait. La ligne 
| | `ret = trace_call_bpf(call, regs);` et `if (!ret) return 0;`. Cela signifie 
| | que si `trace_call_bpf()` retourne _quelque chose d'autre que `0`_ (y compris 
| | `-1`) nous passons par le reste de la fonction, allocation de tampon, stockage 
| | d'arguments de trace, et ainsi de suite. Nous pouvons récupérer les 
| | fonctionnalités internes de cette fonction à [19] :
| | 
| | 
| | ```c
| | /**
| |  * trace_call_bpf - invoke BPF program
| |  * @call: tracepoint event
| |  * @ctx: opaque context pointer
| |  *
| |  * kprobe handlers execute BPF programs via this helper.
| |  * Can be used from static tracepoints in the future.
| |  *
| |  * Return: BPF programs always return an integer which is interpreted by
| |  * kprobe handler as:
| |  * 0 - return from kprobe (event is filtered out)
| |  * 1 - store kprobe event into ring buffer
| |  * Other values are reserved and currently alias to 1
| |  */
| | unsigned int trace_call_bpf(struct trace_event_call *call, void *ctx)
| | {
| | 	unsigned int ret;
| | 
| | 	// ...
| | 
| | 	/*
| |      * ...
| | 	 */
| | 	ret = BPF_PROG_RUN_ARRAY(call->prog_array, ctx, bpf_prog_run);
| | 
| | 	// ...
| | 
| | 	return ret;
| | }
| | ```
| | 
| | Comme vous pouvez le voir, c'est la fonction qui invoque réellement le kprobe. 
| | Elle obtient `ret`, qu'elle retourne, depuis `BPF_PROG_RUN_ARRAY()` qui, 
| | comme vous pouvez vous y attendre, exécute le programme BPF. La documentation 
| | sur cette fonction est également assez explicite, ce qui est agréable. Lorsque 
| | nous retournons `0`, nous avons retourné du kprobe et n'avons pas besoin de 
| | garder des détails à ce sujet traînant. Quand nous retournons `1` (ce que 
| | tout sauf `0` alias vers) nous stockons des informations sur le kprobe dans 
| | un ringbuffer pour plus tard.
| |
| | -...- Solution -...-
| | 
| | La solution ici est de toujours `return 0;` dans vos kprobes, à moins que 
| | vous n'ayez un besoin explicite de `return 1;`. Si vous voulez savoir si 
| | votre kprobe a échoué ou est dans un état incomplet, vous devrez architecturer 
| | votre messagerie pour gérer ce cas. Par exemple, vous pourriez vouloir inclure 
| | un drapeau de code de succès dans la ou les structures que vous passez à 
| | travers un perfmap que vous pouvez vérifier pour l'échec. Ou vous pourriez 
| | vouloir construire votre système autour d'une reconstruction d'événements 
| | best-effort pour des retours plus compliqués impliquant plusieurs messages. 
| | Dans tous les cas, vous devrez concevoir votre vérification et gestion 
| | d'erreurs indépendamment du système VM BPF. Ces codes de retour sont réservés, 
| | vous devez faire les vôtres.
| +-
+-

+-#- Wow, ça a l'air difficile. Peux-tu résumer pour moi ? -#-
| 
| Certainement ! BPF est vraiment bon pour obtenir de la visibilité (presque) 
| n'importe où dans l'ensemble du système, il permet la ré-instrumentation 
| dynamique, peut être rendu conscient des conteneurs, est plus rapide que les 
| alternatives, et est (généralement) sûr à exécuter tant que vous pouvez le 
| charger. Considérez utiliser BPF si l'une des choses suivantes s'applique à 
| vous :
| 
| - Vous avez les ressources internes et l'expertise pour construire et maintenir 
| une source de télémétrie BPF de longue durée.
| 
| - Vous voulez seulement utiliser BPF pour le débogage en direct ou d'autres 
| cas d'usage de courte durée, one shot, comme bpftrace.
| 
| - Vous avez la chance de ne devoir supporter qu'une seule version de noyau.
| 
| - Vous ne vous souciez pas vraiment si le projet réussit, vous voulez juste 
| acquérir de l'expérience avec BPF (ceci pourrait légitimement s'appliquer dans 
| les organismes R&D).
| 
| Si vous n'avez pas les ressources et avez besoin de supporter une large gamme 
| de noyaux, vous seriez mieux de chercher une alternative (il y a beaucoup 
| d'options gratuites et open source grâce à la GPL), ou de payer quelqu'un 
| d'autre pour le construire pour vous.
| 
| Les programmes BPF de longue durée pour la sécurité sont un cas d'utilisation 
| relativement nouveau. L'outillage autour de ce cas d'usage s'améliore tout le 
| temps, mais il y a encore beaucoup à considérer avant de se lancer.
