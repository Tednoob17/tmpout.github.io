[ Traduction par Tedsig42 ]

Juste ce dont j'avais besoin aujourd'hui - un virus implémenté comme une machine 
virtuelle. Au moins il est court.

Linux/Marx est un infecteur direct-action de fichiers ELF x86 64 bits dans le 
répertoire courant, utilisant la technique PT_LOAD. Attachez vos ceintures, nous 
allons parcourir le code à toute vitesse.

OÙ VOULEZ-VOUS ALLER AUJOURD'HUI ?

Le virus est implémenté en utilisant 20 registres généraux, un registre de pile, et 
1504 octets de mémoire scratch (bien qu'il déplace également le pointeur de pile 
réel arbitrairement afin d'accéder à plus de mémoire). Il y a 31 commandes définies, 
mais seulement 29 d'entre elles font réellement quelque chose.

Voici les commandes :

0x02    PUSH reg32
0x03    POP reg64
0x04    MOV reg64_1, reg64_2
0x05    XOR reg64_1, reg64_2
0x06    SYSCALL imm8
0x07    NOP
0x08    SUB reg64_1, reg64_2
0x09    ADD reg64_1, reg64_2
0x0a    MOV reg64, RIP
0x0b    PUSH imm8
0x0c    PUSH imm16
0x0d    PUSH imm32
0x0e    JMP +/- imm16
0x0f    MOV reg8, imm8
0x10    MOV reg16, imm16
0x11    MOV reg32, imm32
0x12    CMP reg64_1, reg64_2 / JNE +/- imm16
0x13    CMP reg64_1, reg64_2 / JE +/- imm16
0x14    MOV reg8, [imm48]
0x15    MOV reg8, [reg64]
0x16    MOV reg16, [imm48]
0x17    MOV reg16, [reg64]
0x18    MOV reg32, [imm48]

0x1b    MOV [reg64], reg8

Nous voyons des instructions pour assigner des valeurs aux registres, lire et écrire 
de la mémoire presque arbitraire (il y a des restrictions), de différentes tailles, 
manipulation de pile, arithmétique basique, transfert de contrôle (conditionnel), et 
appel aux API système... tout ce dont une VM en croissance a besoin. 
Intéressamment, les combinaisons CMP-et-branch sont implémentées comme une seule 
instruction chacune. L'instruction de branchement n'a pas sa propre adresse.


LA TAILLE COMPTE

Ce que nous ne voyons pas de l'extérieur sont tous les petits détails et pièges. 
En interne, chaque instruction fait huit octets de long. Ce format signifie qu'il 
n'y a aucun moyen de travailler directement avec des valeurs 64 bits, malgré les 
registres VM et les emplacements mémoire étant 64 bits en interne. C'est le même 
problème que l'architecture ARM a, mais il manque aussi un pointeur global vers les 
données (il y a accès à RIP, qui pourrait théoriquement permettre l'accès aux 
immédiats relatifs à RIP, mais le virus n'est pas préparé pour les gérer), et aucune 
instruction de shift, donc les valeurs au-delà de 32 bits doivent être construites en 
écrivant en mémoire, soit par adresse (construite), soit en utilisant la pile.

Cela nous mène au plus gros problème de l'implémentation, qui est que les écritures 
mémoire ne font pas d'extension par zéro. Cela signifie qu'un "PUSH imm8" laissera 
56 bits inchangés en mémoire. Cela pourrait être considéré comme un comportement 
acceptable puisque l'instruction ajustera le pointeur de pile d'un seul octet... 
jusqu'à ce que nous essayions de pop la pile. Pourquoi ? Parce qu'un "POP" va 
extraire tous les huit octets de la pile, conduisant à une pile déséquilibrée et 
à la tristesse.

Cependant, cela signifie aussi qu'un "MOV REG32, []" laissera les 32 bits supérieurs 
inchangés, nécessitant un "XOR reg, reg" explicite avant le "MOV" afin d'avoir un 
registre complètement défini. Cela conduit à du code bloat. Étant donné que 
l'utilisation la plus courante des lectures et écritures mémoire est appariée avec 
le XOR, l'ensemble MOV pourrait être réduit à juste le style reg32, ce qui couperait 
huit instructions. Étant donné le nombre de registres disponibles, l'option "imm48" 
pourrait être supprimée aussi, coupant deux autres instructions.

L'ensemble CMP est intéressant aussi. Si les instructions de branchement étaient 
séparées en instructions individuelles, alors il y aurait un seul CMP, et toutes les 
branches pourraient être encodées comme une seule instruction, en utilisant un sous-octet 
pour spécifier le type. Cela permettrait également plus de types de branches.


FAIS MA JOURNÉE

À quoi ressemble le code de virus virtualisé ? Voici un désassemblage.

0000 (0a):    MOV reg[11], RIP

Le virus commence par sauvegarder l'adresse d'exécution. Elle est utilisée plus tard 
lors de l'infection d'un fichier.

0008 (0f):    MOV dil, 0x00
0010 (0f):    MOV sil, 0x00
0018 (0f):    MOV dl, 0x01
0020 (0f):    MOV r10l, 0x00

Ces instructions MOV sont redondantes ici parce que tous les registres sont initialisés 
à zéro par l'interpréteur VM, mais c'est une bonne pratique de programmation de les 
initialiser explicitement.

0028 (06):    SYSCALL 101

ptrace(PTRACE_TRACEME, 0, 1, 0).
Ceci est une technique anti-debugging. Le virus tente de se tracer lui-même, ce qui 
échouera si un debugger est déjà attaché. Silvio Cesare a publié en 1999 un papier sur 
les techniques anti-debugging Linux. Ce papier incluait la valeur non nulle pour le 
paramètre d'adresse. Cependant, on ne sait pas pourquoi il a utilisé cette valeur, 
puisqu'aucun des paramètres n'est jamais lu par le noyau dans une requête TRACEME.

0030 (04):    MOV reg[02], RET
0038 (0f):    MOV dil, 0x00
0040 (12):    CMP reg[02], rdi    
              JNE 0050  
0048 (0e):    JMP 0060

Sauvegarder la valeur de retour de l'appel ptrace(), la comparer avec zéro (ne peut 
pas utiliser l'instruction "CMP ,0" parce que le type de branchement est incorrect). 
Si la valeur de retour est non nulle, c'est une erreur, et une indication qu'un 
debugger est détecté.

0050 (0f):    MOV dil, 0x7b
0058 (06):    SYSCALL 60

Si un debugger a été détecté, alors quitter le processus avec le code d'erreur 123. 
Le code hôte n'est pas exécuté. Le programme vient d'acquérir une protection anti-debugger 
involontairement.

Ceci est un exemple du "doit XOR avant MOV" dû au manque d'extension par zéro. Ce 
problème pourrait être résolu en changeant l'implémentation pour des instructions 
basées sur MOVZX et en écrivant toujours tous les 64 bits.

0628 (02):    PUSH r8         original entry-point
0630 (0d):    PUSH 0xfff4894c mov rsp, r14
0638 (0b):    PUSH 0xe0       jmp rax

Construire ce code en mémoire :

call get_RIP
sub  rax, 0x193
sub  rax, 0x0c000000 + original file size
add  rax, original entry-point
mov  rsp, r14
jmp  rax

C'est ainsi que le virus transfère le contrôle au point d'entrée original de l'hôte 
(OEP) à la fin.

Il est plus facile d'effectuer les opérations individuelles sur le vrai CPU que 
d'essayer de faire l'arithmétique dans la VM.

Vider la mémoire modifiée mappée vers le disque. Maintenant nous avons un fichier 
qui est marqué infecté, avec un point d'entrée altéré, mais pas de contenu viral. 
Nous avons aussi une condition de course avec une requête potentielle pour exécuter 
le fichier avant que l'infection ne soit complète.

Il y a un effet secondaire intéressant à l'opération de sync - l'offset de fichier 
est à la fin du fichier, donc pas besoin de seek là-bas.

0728 (05):    XOR r9, r9

C'était inattendu. 0x1040 était la taille de l'addition, mais il manque le code

CONCLUSION

Écrire même un virus simple est loin d'être simple. Écrire une VM est aussi loin 
d'être simple. Combiner les deux est une recette pour le désastre.
