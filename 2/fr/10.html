Je traîne dans le clubhouse TMP depuis un moment, et l'équipe a décidé de me donner 
le bit d'ELF le plus étrange qu'ils puissent trouver pour mon premier write up. Pour 
ceux qui avaient le téléphone Nokia au collège (vous savez, celui-là) vous vous 
souviendrez du jeu classique "snake". Eh bien, ce jeu de snake vient avec un peu 
d'excitation ELF supplémentaire.

Ceci est une brève introduction à ce code et une analyse plus approfondie pourrait 
avoir lieu ultérieurement.

Le code VIRUS au début est ajouté à la fin du segment text en utilisant la méthode 
"Silvio". VIRUS utilise mmap pour charger VIRUS2 depuis le segment data dans un 
emplacement mémoire qui est exécutable, donc aucun changement de permissions n'est 
nécessaire pour le segment data.

Vous avez peut-être aussi remarqué des fichiers .sh dans la structure de fichiers en 
haut de ce write-up. Ces scripts aident à formater les données à insérer en tant que 
payload en mémoire.

44/Linkeur Interdit\44
4444444444444444444444

Une autre chose que vous avez peut-être remarquée était le script de linkeur sous le 
sous-répertoire snake. Le script de linkeur fait ce que tous les scripts de linkeur 
sont conçus pour faire - rassembler tous les fichiers C et assembly différents pour 
créer un exécutable (dans ce cas, un exe ELF bien sûr !) ce qui en soi ne serait pas 
étrange, excepté pour ce qui se passe ensuite dans ce Makefile ;

---/begin code break\---

CFLAGS=-Wl,-N -fno-builtin -nostdlib -nodefaultlibs -fPIC -pie -mmanual-endbr\
 -fdata-sections -ffunction-sections -s 
all:
    gcc  -c -w $(CFLAGS) -o payload.o payload.c
    
    objcopy --remove-section=.note.GNU-stack payload.o
    objcopy --remove-section=.eh_frame payload.o
    
    ld -s -S -e payload --hash-style=sysv  -N --no-eh-frame-hdr --build-id=none --gc-sections\
        -o payload payload.o --no-dynamic-linker -pie -pic

    objcopy --remove-section=.comment payload
    strip -s payload
    strip -R .dynamic payload
    strip -R .dynsym payload
    strip -R .dynstr payload
    strip -R .eh_frame payload
    
    bash fix.sh

---/end code break\---

Il est intéressant et légèrement non conventionnel (bien que parfaitement fonctionnel) 
de voir objcopy being utilisé comme ça dans un Makefile. Mais attendez, il y a plus !

Vous pourriez penser que la construction de l'exécutable serait la fin de l'histoire, 
mais VXsnake n'est pas encore prêt à révéler le reste de ses secrets. Ces secrets se 
trouvent dans le script fix.sh sous le sous-répertoire second_stage :

---/begin code break\---

#strip shstrtab section and section headers
dd if=./payload of=./TMpayload bs=1 \
    count=$(readelf -S payload | grep shstrtab | awk '{print "0x"$6}' | printf "%d" $(cat /dev/stdin))

 printf "unsigned long payload_entry = 0x%x;\x0a" $(($(cat /dev/stdin)-(64+2*56)-0x400000)) > payload.h

La partie la plus amusante de fix.sh sont les deux dernières lignes où l'exécutable 
payload généré par le script de linkeur est ensuite reconstruit en shellscript C.

66/Retour\66
666666666666

Quel voyage ! Il y a quelques éléments supplémentaires impliqués dans VXsnake que 
nous, honnêtement, n'avons pas encore compris.

Ce que VXsnake fait est de montrer à quel point les constructions ELF peuvent être 
dynamiques, et combien de tours et détours la compilation de code peut prendre. Les 
analystes de malware en particulier devraient prendre note de certaines des techniques 
utilisées par VXsnake pour mieux comprendre à quel point les malwares ELF peuvent être 
compliqués.
